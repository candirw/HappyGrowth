## 2 · 排期

### 排序（按"数据流依赖 + 复利效应"，不按难度）

| 顺序 | 模块 | 为什么排这里 |
|---|---|---|
| **1** | **Part 1 迷你图书馆** | 唯一真相源。它不做，其他四个全缺养分。**且唯一"越早开始积累越值钱"的** |
| **2** | **Part 5 计划系统** | 唯一自带回流闭环。跑通后**每天自动产生数据，复利最强** |
| **3** | **Part 2 外部检索** | 给 Part 1 供料。但按需触发，晚两周无损失 |
| **4** | **Part 4 可行性核查** | 依赖 Part 2 的事实支撑，且要在使用中才能验证有效性 |
| **5** | **Part 3 代码实现** | 前四个都在为它供料。**先做它只能做出空模板** |

### 两个反直觉之处（需要解释，否则会被推翻）

**反直觉之一：Part 5 排在 Part 2 前面。**

直觉上"外部检索"更基础，应该先做。但：

| | Part 5 | Part 2 |
|---|---|---|
| 触发方式 | **每天自动运行** | 按需触发 |
| 积累性 | **每天新增数据，越久越准** | 用一次算一次 |
| 晚做的代价 | **少积累 N 天历史** | 只是晚用 N 天 |

**先跑会产生复利的那一个。**

**反直觉之二：Part 3（写代码）排最后。**

直觉上"写代码是最硬的活，应该先做"。但 Part 3 的产出**依赖前面几个模块的输入质量**：

> 先做 Part 3，你会做出一堆没有素材的脚手架——**模板漂亮，但里面没有点子，因为 Part 1 还没跑起来。**

**排期上的说明：**

- **C1 和 C2 可以并行**（不同人做），因为它们依赖的东西几乎不重叠（C1 是目录与检索，C2 是数据管道与 prompt）。
- **C4 故意排得晚**：核查能力要**在真实使用中验证有效性**。没有 C1/C2 的真实数据，核查只是个空 prompt。
- **C7 放最后但在开始时就要埋点**：模型分级路由的使用习惯要从第一天就养成，否则后面改不及。

## 6 · 我的三条反对意见

写下来防止后面反复讨论，也便于被打脸时回查。

### 反对一：不做 Wiki / 博客

会议纪要原文："文档管理：采用迷你 Wiki 或小型博客形式进行知识沉淀。"

**反对理由：**

1. **已有两套渲染层了**（Obsidian 双链导出 + 本地网页版）。再加 Wiki 是**第三套**。
2. **更关键的是：AI 读不了 Wiki 的前端渲染。** 挂 MCP 时它要的是**纯文本 + 稳定路径**。Wiki 在这个架构里不解决任何问题——它解决的是"多人浏览排版"，而当前是单人（或几人）工具。
3. Wiki 的唯一优势是"让人看着舒服"，而 P2 明确说了**优先级是"方便 AI 读取"**。

### 反对二：不做"向 AI 提问生成需求文档"这一步

会议待办第 3 条。

**反对理由：**

把一份需求文档喂给 AI，让它产出一份需求文档——**这是闭环空转**。AI 只能把你已经说过的话换个措辞。

**真正的信息缺口不在文档格式上，而在「已有资产的边界在哪」：**

| 真正需要回答的 | 为什么只有你能回答 |
|---|---|
| `insight-distiller` 已经覆盖了 5 个模块里的哪些？ | AI 不知道你手头有什么 |
| 哪些是"看起来缺但其实已经有了"？ | 需要对着你的资产清单逐项比 |
| 哪些是真空白？ | 同上 |
| 你实际的工作流是什么样的？ | AI 只能猜 |

**这些做完，文档自己就长出来了。**（本次 `02_复用清单.md` §0 的盘点就是这一步的产出。）

### 反对三：不做健康管理系统（认同用户，但要强调一遍）

用户在订正里已经明确了"**不是健康管理系统**"。这里补充**为什么这个订正极其重要**：

如果按"健康管理"立项，容易走成：

```
❌ 错误路径：采集健康数据 → 分析健康趋势 → 给出健康建议
   → 结果：又一个没人看的健康 App
```

**正确的定位**：

```
✅ 正确路径：采集精力指标 → 因为它是所有计划的前置变量
   → 用来归因"为什么计划执行不动"
   → 结果：AI 真的能让行为发生改变
```

**差别在于：前者以"健康"为目标，后者以"行为改变"为目标，健康数据只是手段。**

这个区别决定了**采集什么、采多少、怎么用**——如果目标是"健康管理"，你会想采更多数据（越多越准）；如果目标是"计划复盘"，你会想**采更少**（够用就行，因为 token 是钱）。

**所以这个订正不只是名字问题，它直接改变了设计方向。**

## 7 · 如果只能做一件事

**做 C1（地基）。**

理由：C1 是唯一**不做就没有其他任何东西**的一环——Part 2 没地方写、Part 3 没素材、Part 4 没对象、Part 5 的复盘结果没处沉淀。

**而且它是唯一"越早开始越值钱"的**：图书馆今天开始积累，一年后有一年的料；三个月后开始，就少了三个月。

**C1 的最小可交付（如果时间很紧）：**

```
1. kb/knowledge/{ideas,docs,frontier,inbox}/ 四个目录
2. 三类 frontmatter 约定（见 03_架构.md §4.2）
3. 把目录接进现成检索层
4. 跑通一个真实样例：丢一个灵感 → 自动提示关联
```

**大约一天。** 不需要等 Part 5、不需要等任何其他模块。
