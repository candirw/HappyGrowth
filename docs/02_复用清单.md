# 02 · 复用清单

> 落地大前提 **P1（能复用就复用，大于重复造轮子）**。
> 每个 Part 先回答"市面上有什么"，再回答"自己该建什么"。

---

## 判定规则（先立规矩，避免每次凭感觉）

复用不是无脑复用。四个问题过一遍：

| # | 问题 | 是 | 否 |
|---|---|---|---|
| 1 | 现成方案解决的是**同一件事**吗？ | 复用 | 看第 2 问 |
| 2 | 现成方案解决的是**同一件事的一部分**吗？ | **接入那一部分**，剩下自建 | 自建 |
| 3 | 接入成本 vs 自建成本，差几倍？ | 差 3 倍以内 → 自建（可控性更值钱） | 复用 |
| 4 | **数据能不能拿出来**？（能否导出为纯文本 / 标准格式） | 复用 | **❌ 无论多好用都不复用** |

**第 4 问是最容易忽略、代价最大的一问**，它直接来自大前提 P2。

> 一个工具再好用，如果你的数据只能留在它的数据库里，那它就是「数据 hostage」。而 P2 明确要求「其他 AI 能读取」——数据拿不出来，P2 直接不成立。

**这条规则会否决掉一些体验很好的 SaaS 笔记工具。** 这是有意的：本地优先（local-first）不是洁癖，是 P2 的硬要求。

### `insight-distiller` 到底覆盖了什么（这是最关键的盘点）

用户对 Part 2 的描述是"外部知识检索工具 + 自动抓"。对照现状：

| 用户要的 | `insight-distiller` 是否已有 | 说明 |
|---|---|---|
| 主动搜（自然语言选材） | ✅ | `distill find` / `plan`，含成本预演与歧义反问 |
| 自动抓（订阅式） | ✅ | `distill subscribe` + 定时任务 |
| 多源采集 | ✅ | B站 / 公众号 / 知乎 / 小红书 / 通用网页 / 本地文件 / PDF |
| 视频转文字 | ✅ | 优先抓字幕，无字幕走本地 Whisper |
| 浓缩 | ✅ | map-reduce 分层浓缩 + 信息密度评分 |
| 可溯源问答 | ✅ | 混合检索（向量+BM25+RRF）+ 带时间戳引用 |
| 论文精读 | ✅ | 四路召回相似论文 + 阅读路径 |
| **入库即自动关联** | ✅ | 三级漏斗，含 `contradicts` 冲突发现 |
| 知识盲区分析 | ✅ | `distill gaps` |
| **区分事实/观点** | ✅ | claim 强制带 `claim_type` / `authority` / `staleness_days` |
| **给外部 AI 读取** | ✅ | MCP Server + HTTP API + Python SDK，共用一套契约 |
| Obsidian 双链导出 | ✅ | `distill vault` |
| 网页版 | ✅ | `distill serve` |

**MCP 出口的现成工具（已核对源码 `agent/mcp_server.py`）：**

| MCP 工具 | 作用 | Part 1/3/4/5 谁用 |
|---|---|---|
| `kb_stats` | 确认知识边界（**先查再答，防止臆断**） | 全部（**每个 agent 应先调这个**） |
| `kb_search` | 按 domain / claim_type / 时效检索，带 token 预算 | Part 4（事实核查）、Part 5（历史对照） |
| `kb_get_claims` | 取原子 claim（已分 fact/opinion/…) | Part 4 |
| `kb_list_conflicts` | **取冲突双方原文** | ★ Part 4（避雷核心） |
| `kb_timeline` | 某主题的认知演进 | Part 2、Part 4 |
| `kb_get_source` | 读某条内容的浓缩（可指定 level） | Part 1、Part 3 |
| `kb_ask` | 带引用的问答 | Part 1、Part 5 |
| `kb_ingest` | **写回知识库**（默认关闭，需显式开启） | Part 3/5 写回 Markdown 时用 |
| `kb_task` | 查询后台任务状态 | — |

**这张表就是"复用而不是重建"的最直接证据**：Part 1 要的检索、Part 4 要的冲突发现、Part 5 要的历史对照，**出口都已经有了**。

**唯一需要注意的**：`kb_ingest` 默认关闭（安全默认值）。若要让 agent 写回，需要在配置里显式开启写接口 + 设 token。**建议仍然坚持"agent 只写 Markdown 文件，由摄入链路进库"**（见 `03_架构.md` §2），而不是让 agent 直接调 `kb_ingest`——后者会绕过 git，失去可回溯性。

**结论：用户的 Part 2 需求，约 80% 已经实现。Part 4 的"领域事实"那一类，约 70% 已由 claim + authority + staleness 机制覆盖。**

这是本次分析最重要的发现——**会议纪要里"要建五个模块"的框架，会让你重写已经存在的东西。**

### `策略研究档案/` 已经是一套知识库目录约定

它的结构值得单独拿出来看，因为它**正是 Part 1 需要的形状，而且是自然长出来的**：

```
策略研究档案/
├── _common/            # 共用工具与数据（跨专题复用）
├── 00_研究计划/        # 计划与日志
├── 02_数据台账/        # 数据源登记
├── 03_实验记录/        # 实验过程与结果
└── 专题_纳指科技股(...)/  # 一个专题一个目录
```

**这套约定里已经包含了 Part 1 要的四个东西**：状态（研究计划）、资产（数据台账）、过程（实验记录）、主题隔离（专题目录）。

**所以 Part 1 不是"从零设计一套知识管理"，而是"把这套已经用顺的约定抽出模板 + 接上检索和关联"。** 工作量差别很大。

## 1 · Part 1 迷你图书馆

### 市面上有什么

按「数据能否拿走」分两类：

**A 类 · local-first，数据是纯 Markdown 文件（✅ 符合 P2）**

| 类别 | 代表 | 能给什么 | 缺什么 |
|---|---|---|---|
| 纯文件笔记 | Obsidian / Logseq | 双链、图谱、插件生态、本地文件 | **不认识"MCP 让 AI 读"这个需求**（Obsidian 需插件桥接） |
| markdown KB + MCP | 一批本地优先工具，直接以目录为库、以 MCP 为出口 | **原生 MCP Server**、FTS5 + 向量混合检索、双链、git 友好 | 大多偏单人，多人权限弱 |
| 结构化对象库 | 类型化笔记工具（对象 + 关系） | 强 schema，适合"灵感/文档/前沿"三类分开建模 | 引入学习成本，且偏离 markdown 纯文本原则 |

**B 类 · 数据在自家数据库（❌ 不符合 P2）**

各类 SaaS 笔记 / 团队 Wiki。**体验通常最好，但数据拿不出来（第 4 问否决）。** 不用考虑。

### 我的建议：**不引入新工具当主体，用「目录约定 + 现成检索层」**

理由：

1. **`insight-distiller` 已经有一整套检索与关联能力**（混合检索 + RRF + 三级漏斗关联 + claim）。再引入一个笔记工具的检索，就是两套索引、两套关联、两套 embedding——**这才是真正的臃肿**。
2. **Part 1 的核心难点不是"用什么工具写笔记"**，是"关联性优秀"和"三类内容生命周期不同"。这两个都是**数据模型问题**，不是编辑器问题。
3. 用户已有 `策略研究档案` 这套顺手的约定。

**所以复用策略是分层的：**

| 层 | 复用谁 | 说明 |
|---|---|---|
| **存储** | **纯 Markdown 目录**（复用 `策略研究档案` 的约定，抽成模板） | 唯一真相源，git 可管 |
| **检索** | **`insight-distiller`**（混合检索 + 关联漏斗 + claims） | 不重新实现 |
| **AI 出口** | **`insight-distiller` 的 MCP Server** | 已经存在，直接复用 |
| **人类浏览** | **Obsidian**（读同一个目录，可选） | `distill vault` 已能导出双链，直接用 |
| **多人协作** | **git** | 用户已经在用 |

**唯一需要新写的东西：** 三类内容的 schema（frontmatter 字段约定）+ 一个把目录喂给 `insight-distiller` 的薄封装。见 `03_架构.md` §4。

> **为什么不用通用笔记工具当主体**：它会成为第三套索引。而现在最需要避免的恰好是「三套索引」——这也正是 P1 想防的事。

## 2 · Part 2 外部检索

### 市面上有什么

用户说"网上已经有 ai 自动抓前沿论文、热点、投资讯息的基建了"——**这个判断是对的**。分层看：

| 层 | 现成方案 | 该自建吗 |
|---|---|---|
| **数据源** | 论文：arXiv API / HuggingFace Daily Papers / Semantic Scholar / OpenAlex / Crossref<br>通用：RSS、RSSHub（能把大量没有 RSS 的站点转成 RSS）<br>代码：GitHub Trending / API<br>行情：公开行情 API | ❌ **完全接入** |
| **调度** | 系统任务计划 / cron / 各类 workflow 工具 | ❌ **完全复用** |
| **抓取 + AI 摘要** | 开源项目很多：arXiv 每日精选 + LLM 中文摘要 + 推送到飞书/Telegram/邮件这一类，已相当成熟；也有以 Agent Skill 形式分发的版本，一句话触发 | ⚠️ **看情况**：能接入就接入，见下 |
| **筛选与消化** | **普遍很弱** | ✅ **这才是要自建的地方** |

### 关键判断：抓取是商品，筛选才是能力

市面上的 arXiv 追踪工具普遍做了这三件事：抓 → 摘要 → 推送。

**它们共同的问题恰好是用户最担心的事**：它们**没有丢弃机制**。

```
抓 30 篇 → 全部摘要 → 全部推送 → 用户第三周就不看了
                                  ↓
                          但工具还在每天推 30 篇
```

**而 `insight-distiller` 已经有解决这个的东西了**：信息密度评分（能区分水文和实质内容）+ 未读折旧 + 关联提示。

**所以正确的复用姿势是：**

```
【复用】现成的抓取器  →  只负责"把候选带到本地"
【复用】cron/任务计划 →  只负责"定时拉起"
【自建】筛选 + 消化   →  ★ 用 insight-distiller 的密度评分 + 浓缩 + claim 抽取
【自建】丢弃机制      →  ★ 密度低于阈值的不入库，只在日报留一行统计
```

**即：抓取直接抄现成的，消化链路用自己的。** 这样既避免了重复造抓取轮子（P1），又保住了消化质量（P2）。

### 具体缺口清单

| 缺口 | 现有覆盖 | 建议 |
|---|---|---|
| 播客 RSS | ❌ | **建议做**。`insight-distiller` 已能处理本地音频，只需加"解析 feed + 下载 enclosure"，约 1 天 |
| 论文自动抓（定时） | 🟡 有 `add` 但无自动发现 | **接入现成抓取器**，或基于 arXiv API 写一个约半天的 adapter |
| 热点 / 行业资讯 | 🟡 RSSHub 可覆盖大部分 | **用 RSSHub + `subscribe`**，不自建 |
| YouTube | ❌ | 按需，约半天 |
| **投资讯息的时效与权威度** | ✅ claim 已带 `staleness_days` / `authority` | **复用**，但需在消费侧强制过滤 |
| **综述（陌生领域）** | 🟡 零件齐全，无入口 | ✅ **要自建一个命令**，见 §4 |

**只有"综述入口"这一条是必须新写的**，其余都是接入或小补丁。

> 综述的价值不在"多抓几篇"，而在**先建领域分区 → 落地 claim → 把冲突显式摆出来**。这三步 `insight-distiller` 全都有（`domain` / `claims extract` / `conflicts`），缺的只是串起来的命令。

## 3 · Part 3 代码实现

### 市面上有什么

| 需求 | 现成方案 | 复用判断 |
|---|---|---|
| 项目状态机 | GitHub Issues / Projects | ✅ 复用（免费且够用） |
| 版本控制 | git / GitHub | ✅ 复用 |
| CI/CD | GitHub Actions | ✅ 复用 |
| **环境隔离** | venv / uv / conda / devcontainer | ✅ 复用 |
| 依赖管理 | uv / poetry | ✅ 复用 |
| **AI 协作的项目上下文约定** | 有一批现成范式（如各种 `AGENTS.md` / spec-driven 工作流约定） | ✅ **复用范式，不造** |
| 点子池 / 想法管理 | 笔记工具 + 标签 | ✅ 复用 Part 1 |
| 代码片段 / 灵感速记 | 编辑器内置 | ✅ |

### 关键判断：**Part 3 几乎不需要自建系统**

用户说"这里面要配套工具、管理系统等等"。但逐项看下来：

- **项目管理** → GitHub 已经免费给了，自建必然更差
- **版本控制** → git 已经解决了
- **环境** → uv/venv 已经解决了
- **点子到项目的流转** → 这是 Part 1 的职责，不是 Part 3 的

**真正需要自建的只有一样：一套「项目脚手架模板」。**

理由：Part 3 的真实痛点是「**每次让 AI 帮忙都要重新解释项目现状**」和「**二十个半成品**」。这两个都不是靠"系统"解决的，是靠**约定文件**：

```
template/
├── README.md        # 这是什么、怎么跑
├── PLAN.md          # 需求与设计
├── PROGRESS.md      # ★ 当前状态 / 下一步 / 已知坑（AI 每次先读这个）
├── DECISIONS.md     # 为什么这么选（防 AI 反复推翻已定方案）
└── .gitignore       # 含 .venv / data / secrets
```

**这四个文件不是文档，是 AI 的输入接口**——这正是 P2（"方便其他 AI 读取"）在 Part 3 的落地。

**工作量：约半天。** 而自建一套项目管理系统的性价比是负的。

### 一个必须立的纪律（防止半成品）

> **不允许存在"状态不明"的项目。**

每个 projects 下的项目，`PROGRESS.md` 头部必须有一行状态：

```
状态：设想 | 在做 | 暂停（原因） | 完成 | 废弃（原因）
```

**连续 30 天无 commit 的项目，必须被显式标为「暂停」或「废弃」，并写明原因。**

这不是管理洁癖——**最臃肿的从来不是大模块，是二十个说不清状态的小项目**。这条纪律比 git 更能防臃肿。

## 4 · Part 4 可行性 / 准确性核查

### 这部分市面上基本没有现成的

原因很简单：**这是个人化的诉求**（"我不懂这个领域，帮我避雷"），而市面产品都是面向通用问答的。

能复用的只有**零件**：

| 要的能力 | 复用谁 |
|---|---|
| 领域事实核查（"这领域现在什么样"） | **`insight-distiller`**：多源采集 + claim 的 `fact`/`opinion` 分离 + `authority` + `staleness_days` |
| 冲突发现（"有相反观点吗"） | **`insight-distiller`**：`distill conflicts` |
| 知识盲区（"我漏了什么"） | **`insight-distiller`**：`distill gaps` |
| **行动陷阱核查（"我会在哪翻车"）** | ❌ **无现成方案，必须自建** |

**所以 Part 4 只有一小块要建，但它是最关键的一块**：一个**强制 AI 扮演反对者**的 prompt 模板。

**为什么必须自建**：默认状态的 AI 是"顺着你说"的（因为它被训练成有帮助）。你要的恰好相反。这不是能力问题，是**没有工具会主动给你这个**。

**实现成本：极低（纯 prompt + 一个入口命令）。价值：极高。** 这是整份方案里性价比最高的一项。

详见 `04_各模块设计.md` §4。

## 5 · Part 5 计划系统

### 市面上有什么

| 需求 | 现成方案 | 判断 |
|---|---|---|
| 手环数据导出 | 各厂商官方 App 导出 CSV / 第三方桥接（如把健康数据同步出来的工具） | ✅ **复用**，不要自己对接 SDK |
| 计划 / 打卡 / 习惯 | 大量 App | ❌ **但仍不该用**——理由见下 |
| 屏幕使用时间 | 系统自带 | ✅ 复用 |
| 番茄钟 / 专注记录 | 大量工具 | ✅ 复用 |
| **AI 制定计划 + 复盘** | ❌ 现成产品都是"生成计划"，**没有闭环** | ★ **自建** |

### 关键判断：**不要用现成的打卡 App**

理由是两个，第二个才是决定性的：

| 理由 | 说明 |
|---|---|
| 1 | 打卡 App 都要求**主动上报**（每天点一下）——**这是摩擦，必然死掉** |
| 2 | **它的数据你也拿不出来**（第 4 问否决）。而 Part 5 的核心恰恰是"让 AI 读这些数据做复盘" |

**所以数据流必须是：`手环/系统 → CSV → 文件 → AI`**，**中间不能有任何要求人工操作的环节**。

### 因此需要自建的部分

| 要建的 | 工作量 | 说明 |
|---|---|---|
| **数据管道**：手环导出 → 日聚合 CSV → 入库 | 小 | 这是**唯一的前置阻塞项**（取决于手环是否支持自动导出） |
| **计划模板 + 三条硬约束** | 小 | 见下 |
| **复盘归因框架** | 小 | 见 `01_需求对齐.md` Part 5 的四类归因 |
| 提醒 / 打卡 | **不做** | 那是摩擦，不是助力 |

**计划生成的三条硬约束**（这是核心资产，务必写进模板）：

```
① 第一步必须能在 5 分钟内开始
② 一次只给一条建议（给五条 → 一条都不执行）
③ 必须明确"什么时候、在哪里、做什么"
```

**复盘的核心洞察**（整份文档里我最看重的判断）：

> **多个不相关的计划同时下滑 → 原因几乎不可能是"自律变差了"，而是上游输入（睡眠/精力）出了问题。**

这条推论有两个直接结果：

1. **解释了为什么需要手环数据**——不是为了"管理健康"，而是**精力是所有其他计划的前置变量**。这让 Part 5 和手环的关系变得自然。
2. **给出可操作的诊断顺序**：先查"是否多计划同时下滑"，是 → 查上游；否 → 再查单计划归因。

## 汇总：真正要建的东西只剩这些
