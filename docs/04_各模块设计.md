# 04 · 各模块设计

> 逐个模块的落地设计。每个模块回答：**核心机制是什么 / 具体怎么做 / 反直觉之处 / 怎么验收**。
> 架构（目录、索引、出口）见 `03_架构.md`，这里只讲每个模块自己的东西。

## Part 1 · 迷你图书馆

### 核心机制：三类内容分离 + 被动关联

设计细节见 `03_架构.md` §4。这里补三个**容易做错、但决定成败**的点。

### 关键点一：三类内容的区分标准（不是按格式分，是按生命周期分）

| 类型 | 判据 | 时效 | 有版本吗 | 归宿 |
|---|---|---|---|---|
| **灵感** | 是我冒出来的，无外部触发 | 长 | **无** | 攒着，等被激活 |
| **文档** | 我在系统性地写它 | 长 | **有** | 是产出物，会被引用 |
| **前沿** | 外部世界发生了事 | **短** | 无 | 要么转成我的判断，要么归档 |

**最容易做错的是把"前沿"和"灵感"混在一起。** 会议纪要其实已经点了（"独立于灵感池建立热点追踪机制"），但没有把"文档"也分出去——**三类，不是两类**。

**为什么必须分**：灵感可以无限攒；前沿有保质期。混在一起的结果是**前沿淹掉灵感**，而前沿的价值恰恰在"过期前必须处理"。

### 关键点二：`frontier/` 的防腐机制

这是 Part 1 最容易退化成"收藏夹坟场"的地方。三个机制：

| 机制 | 实现 | 效果 |
|---|---|---|
| **`expires` 必填** | frontmatter 强制 | 到期自动归档，不再占列表 |
| **`verdict` 追踪** | `null` 超 90 天 → 周报提示 | 逼自己"消化掉"，而不是"存起来" |
| **归档而非删除** | 移入 `frontier/_archive/` | 保留"我当时关注过什么" |

**核心理念：前沿方向的价值不在于"存了多少"，而在于"转化了多少"。**

### 关键点三：关联的提示必须带原文，不能只给"相关"

```
❌ 错误：找到 2 条相关内容
✅ 正确：⚠️ 与 ideas/2026-08-15-手环数据.md 结论冲突
          本文：日聚合足够
          对方：原始数据才有分析价值
```

**必须展示双方原文主张**，否则用户无法判断，提示就变成了噪音。这条纪律来自 `insight-distiller` 的既有设计，值得原样沿用。

### 验收

| # | 标准 | 怎么测 |
|---|---|---|
| 1 | 三类内容不混（各自目录 + frontmatter 校验） | 有校验脚本 |
| 2 | 新入库自动提示关联，且**必带双方原文** | 抽查 10 次 |
| 3 | `frontier/` 无超 90 天未处理条目 | 巡检 |
| 4 | 冲突记录有累积（说明真在发现矛盾） | 季度统计 |

## Part 2 · 外部检索

### 核心机制：Pull / Push 分离 + 丢弃机制

用户明确点了**两种模式**（"需要主动搜的" + "自动化抓的能力"）。它们**风险方向相反**，必须分开设计：

| 模式 | 风险 | 对策 |
|---|---|---|
| **Pull（主动搜）** | 搜不到 / 搜偏了 | 成本预演 + 歧义反问（**现成**） |
| **Push（自动抓）** | **噪音淹死** | ★ **丢弃机制**（要补） |

### 关键点一：自动抓的评价标准不是覆盖率，是阅读率

所有自动抓系统的共同死法：

```
第 1 周：很兴奋，每篇都看
第 3 周：开始不点开
第 6 周：静默关掉 —— 但它还在占着存储和注意力预算
```

**所以自动抓必须具备"丢弃机制"，而不是"收集机制"：**

| 机制 | 阈值（初始值，可调） | 效果 |
|---|---|---|
| 密度门槛 | 密度 < 50 不入库 | 只在日报留一行"过滤掉 N 篇" |
| 日报上限 | **Top3** | 推 30 篇 = 没推 |
| 未读折旧 | 90 天未碰 → 降级为"存在但不再推" | 防止坟场 |

**反直觉之处：`覆盖了多少源` 是虚荣指标，`用户实际读了百分之几` 才是。**

**这条直接改变了一个常见做法**——不要追求"覆盖 30 个源"，**覆盖 3 个高频源 + 会丢弃 > 覆盖 30 个低频源 + 全推**。

### 关键点二：抓取复用现成，消化自建

用户的判断是对的（"网上已经有基建了"）。分层：

```
【复用】现成抓取器（arXiv 追踪 / RSS / RSSHub / 热点类项目）
        → 只负责"把候选带到本地"
【复用】cron / 系统任务计划
        → 只负责"定时拉起"
【自建】筛选 + 消化  ★
        → 密度评分 + 浓缩 + claim 抽取（现成能力，需串起）
【自建】丢弃机制      ★
        → 密度低于阈值不入库
```

**一句话：抓取和调度是商品（commodity），筛选和消化才是能力。**

> 把精力花在自行实现爬虫和定时器上，是这个方案里最典型的造轮子。

### 关键点三：`survey` 综述命令（唯一必须新写的入口）

陌生领域补课的样子，是一个命令而不是"多抓几篇"：

```bash
distill survey "量子计算退相干" --depth 2 --max-sources 15

# 内部串起已有能力：
#   discover → 批量 add → 建 domain 分区 → claims extract
#            → conflicts 分组 → 输出三段
```

**输出必须是三段**，这是它区别于"随便搜搜"的关键：

| 段 | 内容 | 来源 |
|---|---|---|
| **共识** | 多源一致、且来源权威的 | claim `type=fact/data` 且多源 |
| **分歧** | 有相反主张的，**附双方原文** | `contradicts` 关系 |
| **存疑** | 只有单一来源 / 来源不明 / 时效过期 | 权威度或时效不达标 |

**这三段直接消灭了"望文生义导致的认知偏差"**——因为输出强制区分了 `fact` / `data` / `opinion` / `prediction`，而权威度和时效是 schema 里的 required 字段，**模型没法把自媒体口径伪装成事实**。

### 关键点四：投资类信息的硬约束

用户提到了"投资讯息"。这类信息两个特殊性：
- **时效性极强**——两周前的判断可能是错的
- **观点与事实极易混淆**——自媒体口径和官方公告不能等权

**硬约束（不是建议）：** 消费投资类知识时，`as_of` / `authority` / `claim_type` 必须在 schema 层面 required。**否则下游任何 AI 消费它都会做出错误决策。**

### 验收

| # | 标准 | 怎么测 |
|---|---|---|
| 1 | Pull：一句自然语言 → 候选 + 成本预估 → 确认后批量消化 | 端到端跑通 |
| 2 | Push：**连续 30 天，每天主动读 ≥1 条** | 有阅读记录 |
| 3 | 入库量 : 过滤量 可观测 | 日报有统计 |
| 4 | 投资类信息每条带时效与权威度 | schema required |
| 5 | 源失效时明确报错，不静默空返回 | 有失败清单 |

## Part 3 · 代码实现

### 核心机制：状态机 + AI 上下文接口

### 关键点一：这里几乎不需要自建系统

用户说"要配套工具、管理系统"。但逐项看：

| 需求 | 现成方案 | 自建？ |
|---|---|---|
| 项目管理 | GitHub Issues / Projects | ❌ 免费且够用 |
| 版本控制 | git | ❌ 已解决 |
| CI | GitHub Actions | ❌ |
| 环境隔离 | uv / venv | ❌ |
| 点子到项目的流转 | **Part 1 的职责** | ❌ 不归 Part 3 |

**真正要建的只有一个东西：项目脚手架模板。** 工作量约半天。

### 关键点二：模板的四个文件是 AI 的输入接口（P2 的落地）

```
projects/<项目名>/
├── README.md        # 这是什么、怎么跑起来        ← 给人和 AI
├── PLAN.md          # 需求与设计                  ← 给人和 AI
├── PROGRESS.md      # ★ 状态 / 下一步 / 已知坑     ← 给 AI（每次先读这个）
└── DECISIONS.md     # 为什么这么选                 ← 给 AI（防反复推翻已定方案）
```

**这四个文件不是文档，是接口。** 直接回应 Part 3 的真实痛点：

> 每次让 AI 帮忙都要重新解释：这是个什么项目、技术栈是什么、上次做到哪、踩过什么坑。**这个成本累积起来远超写代码本身。**

`PROGRESS.md` 的模板：

```markdown
状态：在做            # 设想 | 在做 | 暂停（原因） | 完成 | 废弃（原因）

## 当前做到哪
- [x] 数据管道跑通
- [ ] 归因框架还没接

## 下一步
接复盘归因

## 已知坑
- 手环导出的 CSV 时区是 UTC+0，导入时要转
- 用 A 库的 2.x 会报错，锁 1.9
```

**"已知坑"这一节是模板里最有价值的一行。** 它防止 AI 反复踩同一个坑，也防止你三个月后忘记当初为什么绕路。

### 关键点三：防半成品的纪律（比 git 有效）

**真正的敌人不是"写不出代码"，是"写了一半"。**

```
状态机：设想 → 调研 → 在做 → 暂停(原因) → 完成 / 废弃(原因)
```

**硬规矩：连续 30 天无 commit → 必须显式标为「暂停」或「废弃」，并写明原因。**

| 反直觉之处 | 说明 |
|---|---|
| **不允许"状态不明"的项目** | 这才是臃肿的真正来源 |
| **"废弃"是正常状态，不是失败** | 允许废弃 + 记录原因，比硬撑着做要好 |
| **最臃肿的不是大模块** | 是二十个说不清状态的小项目 |

> **git 管不住臃肿。** git 只保证可回滚。防臃肿靠的是准入规则（`inbox/`）和状态纪律（这条）。

### 关键点四：复现类任务要有 checklist

用户用了"**复现**新刷到的点子"——这类任务和自研完全不同：

| | A 复现 | B 自研 |
|---|---|---|
| 主要工作 | 读代码 + 配环境 + 最小改动 | 设计 + 写 + 迭代 |
| 失败方式 | 环境配不起来 / 改散了 | 半途而废 / 越写越大 |
| 关键动作 | **先跑通原版，再改一行** | 先定验收标准 |

**复现 checklist：**
```
① fork / clone，先跑通原版（不改任何代码）
② 记下环境要求到 PROGRESS.md
③ 确认"跑通"的定义是什么（输出了什么算成功）
④ 只改一行，验证改动生效
⑤ 才开始真正的改造
```

**第 ④ 步最关键**：很多人跳过它直接大改，结果出了问题不知道是自己的改动还是环境。**"只改一行先验证链路"是复现类任务最重要的一条经验。**

### 验收

| # | 标准 | 怎么测 |
|---|---|---|
| 1 | 新建点子项目 ≤5 分钟（含环境） | 用模板实测 |
| 2 | AI 读 `PROGRESS.md` 后能复述现状与下一步 | 实测一次 |
| 3 | 无"状态不明"的项目 | 月度巡检 |
| 4 | 复现类任务按 checklist 走 | 有记录 |

## Part 4 · 可行性核查

### 核心机制：三类问题拆解 + 强制反对

**这是整份方案里性价比最高的一项**：实现成本极低（纯 prompt），价值极高。

### 关键点一：先把"可行性核查"拆成三类（否则做糊）

用户说"核查可行性和准确性"，太宽。按**事的性质**拆：

| 类型 | 问题形态 | 本质 | 解法 | 复用谁 |
|---|---|---|---|---|
| **A 领域事实** | "这世界现在什么样" | 检索问题 | 多源交叉 + 事实/观点分离 | ✅ `insight-distiller` |
| **B 行动陷阱** | "我这么做会在哪翻车" | **对抗性问题** | ★ 强制 AI 扮演反对者 | ❌ **必建** |
| **C 边界与成本** | "理论上可行吗、值不值" | 约束问题 | 显式列资源/时间/能力约束 | 部分现成 |

**B 类是核心，也是用户说的"避雷"的本义。**

### 关键点二：默认状态的 AI 是"帮凶"，不是"避雷针"

这是 Part 4 最重要的一句判断：

> **默认状态的 AI 倾向于顺着你的思路往下推**（"这个方案很好，可以这样做…"），因为它被训练成有帮助的。而你要的恰好相反——**你要它拦你**。

**这不是能力问题，是没有任何工具会主动给你这个。** 所以必须显式设计。

### 关键点三：核查 prompt 模板（可直接用）

```
你不是顾问，是对手。用户要执行下面这个方案。

【方案】
{粘贴 plan / 描述}

【用户自述的相关背景】
{正在用的工具链、技术栈、时间预算、已知限制}

请找出这个方案最可能失败的 3 个具体原因。要求：

① 每个原因必须是"在什么条件下会失败"，不是泛泛的风险
   反例：可能性能不够（❌ 太空）
   正例：当数据量超过 10 万条时，这个查询会走全表扫描，
        在当前 SQLite 单文件方案下会超过 2 秒（✅ 具体）

② 至少 1 个必须来自"用户没说、但显然没考虑到的地方"
   例如：部署环境、数据迁移、依赖废弃、维护成本

③ 如果确实找不到 3 个，就直说"这个方案问题不大"——
   不要凑数。硬凑的废理由会让用户忽略真问题

④ 禁止给安慰性表述。不要写"总体可行，注意XX即可"，
   也不要在最后补一段"当然这个方案也有很多优点"
   —— 优点用户自己知道，你只需要给反对意见

⑤ 区分三档置信度：
   【确定】有明确依据 → 给出出处
   【存疑】知道有争议但没把握 → 明确写"需你实际验证"+给验证方法
   【未知】超出你知识范围 → 直接说不知道，并建议去哪里查
```

**第 ③④⑤ 条是这份模板的精髓，逐条说明为什么：**

| 条款 | 不写会怎样 |
|---|---|
| ③ 找不到就说问题不大 | AI 会**硬凑三个废理由**，稀释真问题 |
| ④ 禁止安慰表述 | AI 会用"总体可行"把三个真问题**冲淡掉** |
| ⑤ 区分置信度 | **双方都不知道对方不知道**——最危险的状态 |

### 关键点四：置信度三档是硬要求

用户说"每个人的专业知识有限，注定要在很多自己不了解的地方实现想法"。但**AI 在那些地方也不一定了解，而且它不会主动说。**

| 状态 | 含义 | 输出要求 |
|---|---|---|
| **确定** | 有明确依据 | 给出依据出处 |
| **存疑** | 知道有争议，没把握 | 明确写"需你实际验证"+ 验证方法 |
| **未知** | 超出知识范围 | **直接说不知道** + 建议去哪查 |

> **一个不说"我不知道"的核查系统是负资产——它会给你虚假的安全感。**

**验收方式很直接：如果核查输出里从来没出现过"未知"，说明它在硬答。**

### 关键点五：必须是横切能力，不能是独立系统

**没有人会主动去"跑一个核查工具"。** 它必须内嵌在另外四个模块的自然流程里：

| 在哪 | 触发时机 | 查什么 |
|---|---|---|
| Part 1 写灵感 | 标记为 `exploring` | 这想法现实吗 |
| Part 2 读到结论 | 结论要进库 | 这结论可信吗（→ 走 A 类） |
| **Part 3 动手前** | 写 `PLAN.md` 时 | ★ 这方案会怎么翻车（→ 走 B 类） |
| Part 5 定计划 | 计划生成后 | 这计划能坚持吗 |

**如果 Part 4 需要用户"专门去做"，它就等于不存在。**

### 关键点六：核查也要分层，不能无脑全查

| 分层 | 触发 | 深度 | 成本 |
|---|---|---|---|
| L0 | 每次 | 3 秒自问"这需要查吗"（人判断） | 零 |
| **L1 快查** | 想法进入 `exploring` | 单个 prompt，找 3 个翻车理由 | **一次调用** |
| **L2 深查** | 真准备动手 | 多源交叉 + 领域分区 + 冲突显式化 | 较高 |

**默认走 L1。** 大部分想法不需要 L2。

### 验收

| # | 标准 | 怎么测 |
|---|---|---|
| 1 | 有 ≥3 条"核查后放弃/修改"的案例 | 有记录 |
| 2 | 输出里**没有**"总体可行"这类空话 | 抽查结构 |
| 3 | **说出过"不知道"** | 从来没说过 = 在硬答 |
| 4 | 不打断主流程（内嵌而非独立步骤） | 无额外操作 |

## Part 5 · 计划系统

### 核心机制：副产品采集 + 归因框架

**注意：这一 part 不是健康管理。** 健康数据只是**输入之一**。主题是：

> **如何让 AI 的建议真正改变一个人的行为。**

### 关键点一：数据必须是行为的副产品

**这是整份文档里我最想强调的一条。**

> **任何需要用户"主动填表"的方案都会在两到四周内死掉。**
> 不是意志力问题，是**摩擦成本 > 收益**时的必然结果。

| 计划类型 | ❌ 上报式（会死） | ✅ 副产品式 | 摩擦 |
|---|---|---|---|
| 英语 | "今天学了多久" | 背单词 App 打卡导出 / 阅读器生词本 | 0 |
| 专注力 | "今天专注了几小时" | 屏幕使用时间 / 番茄钟自动记录 | 0 |
| 膳食 | "今天吃了什么" | 外卖订单 / 相册 + 时间戳 | 低 |
| 精力 | "睡得怎么样" | 手环自动同步 | 0 |
| 运动 | "今天动了吗" | 手环 / 运动 App | 0 |

> **"低成本给 AI 提供信息"的真正含义不是"少填几个字"，而是"用户什么都不用做"。**

**推论：不要用现成的打卡 App。** 两个理由，第二个才是决定性的：
1. 它要求主动上报（摩擦 → 必然死）
2. **它的数据你拿不出来** → AI 读不到 → Part 5 的核心（复盘）直接不成立

### 关键点二：计划生成的三条硬约束

```
① 第一步必须能在 5 分钟内开始
② 一次只给一条建议
③ 必须明确"什么时候、在哪里、做什么"
```

**第 ② 条最反直觉也最重要：**

> **给用户 5 条建议，实际结果是 0 条被执行；给 1 条，执行率反而高。**
> 市面上的健康/学习类 App 都栽在这里。

**第 ① 条的作用**："减少摩擦 > 降低难度"。一个"每天背 50 个单词"的计划失败，往往不是因为 50 个太难，而是因为**开始这个动作太重**。改成"每天打开 App 看一眼"反而能成——**先让它发生，再让它变好。**

### 关键点三：复盘的四类归因框架（用户提到"贪玩、精力不足"，这里补完整）

用户问的是"为什么某些计划执行得不够好，服从度够不够，是不是因为贪玩、精力不足"。

**必须有固定的归因框架**，否则复盘会变成互相找借口或自我责备。四类原因，四种解法：

| 归因 | 典型表现 | 正确解法 | **关键判据** |
|---|---|---|---|
| **① 能力不足**（太难） | 开始后 5 分钟内就中断 | **拆小**，拆到"5 分钟能开始" | 中断点集中在开头 |
| **② 动机不足**（不想做） | 压根没开始，但不是没时间 | **换目标或重定意义**——这真是你要的吗 | 有整块空闲但没做 |
| **③ 环境不利**（没时间/被打断） | 开了头但被外部打断 | **改场景**：换时间、换地点、切通知 | 中断点分散在全程 |
| **④ 精力不足**（疲劳） | 完成度整体下滑 | **先解决上游**——这往往不是自律问题 | ★ **多个计划同时下滑** |

### 关键点四：第 ④ 类是整份设计最有价值的一处洞察

> **如果多个不相关的计划同时出现执行率下滑，原因几乎不可能是"自律变差了"，而是上游输入（睡眠/精力）出了问题。**

这条推论带来两个直接结果：

**结果一：它解释了为什么需要采集精力指标。**
不是为了"管理健康"，而是因为**精力是所有其他计划的前置变量**。这让 Part 5 和手环数据的关系变得自然——数据放进来，是因为它影响别的计划，不是因为"我们想管健康"。（这也正好回应用户的订正："不是健康管理系统"。）

**结果二：它给出了可操作的诊断顺序。**

```
发现计划执行率下滑
        ↓
① 是不是多个不相关计划同时下滑？
        ├─ 是 → 查上游（睡眠/精力）→ 改上游，不改计划
        └─ 否 → 继续
        ↓
② 中断点在哪？
        ├─ 集中在开头 → ① 能力不足 → 拆小
        ├─ 分散在全程 → ③ 环境不利 → 改场景
        └─ 压根没开始 → ② 动机不足 → 换目标
```

**这个诊断树是 Part 5 的核心资产**，也是它区别于"AI 生成学习计划"的地方。

### 关键点五：数据量必须压到 AI 读得起

用户说"足量信息"，但**足量 ≠ 多**。上下文有配额（token 就是钱）：

| 采集方式 | 每天量 | 能读吗 | 判断 |
|---|---|---|---|
| 低清截图（每分钟1张） | 1440 张 | ❌ | 只做**异常时取证** |
| 手环秒级心率 | 86400 点 | ❌ | 必须日聚合 |
| **手环日聚合** | **约 80 token** | ✅ | ★ **正确粒度** |

会议纪要把"低清摄像头"和"手环"并列了，实际**成本差三个数量级**。先做日聚合。

### 关键点六：回流闭环（Part 5 独有的架构特征）

```
① 采集（零人工）  手环自动同步 → 日聚合 → data/wearable/YYYY-MM.csv
                                    ↓
② 入库            作为结构化数据进库
                                    ↓
③ 分析（AI 主动）  与历史比对 → 输出「偏离项 + 1 条建议」
                                    ↓
④ 建议必须满足     ① 5 分钟能开始 ② 只提一条 ③ 明确何时何地做
                                    ↓
⑤ 复盘（周度）     执行了吗？没执行 → 走上面的诊断树
```

**Part 5 是五个模块里唯一自带回流的**：产出行为后产生新数据，回流进知识库。**这也是它能产生复利的原因**——跑得越久，历史对照越多，归因越准。

### 验收

| # | 标准 | 怎么测 |
|---|---|---|
| 1 | 用户**每日主动操作次数 = 0** | 全自动流入 |
| 2 | 连续 14 天有数据 | 中断即失败 |
| 3 | 产生过 ≥1 条**被实际执行**的建议 | 有执行记录 |
| 4 | 复盘能区分四类归因，而非笼统说"坚持不够" | 抽查输出 |
| 5 | "多计划同时下滑"时能指向上游 | 有诊断记录 |

## 题外话 · AI 文娱

### 判断：同意用户的看法，而且这正好验证了架构

用户的原话是"这些都是可以给予前面的几大模块实现的"。逐项映射：

| AI 文娱要做的事 | 实际上是 | 归属 |
|---|---|---|
| 制定教程、沉淀方法 | 写**文档** | Part 1（`docs/`） |
| 制定学习计划、跟进度 | **计划 + 复盘** | Part 5 |
| 分析行业方向、追踪工具 | **外部检索 + 综述** | Part 2 |
| 核查"这方向能不能做" | **可行性核查** | Part 4 |
| 实际上手试一遍 | **代码/项目** | Part 3 |

**结论：AI 文娱不是一个新模块，是前五个模块的一个应用场景（Domain）。**

> **这正是好架构的特征——不需要为新领域加新模块。** 如果每次出现新兴趣都要加一个系统，那架构就是错的。

### 但要立一条纪律

这是会议待办里**最危险的一条**，因为它听起来最轻松（"各自认领一个方向实践探索"）。

| 风险 | 后果 | 纪律 |
|---|---|---|
| 探索性任务抢主线的注意力 | 五个模块都做一半，文娱也没做成 | **只在前四个模块的框架内做**，不为它开新系统 |
| "制定教程"变成无边界大工程 | 写不完，不了了之 | **一篇教程 = 一次 Part 1 入库**，不做"课程体系" |
| 产量导向 | 追数量，质量崩 | 判据是"我自己上手成功了吗"，不是"写了多少" |

**一句话：AI 文娱的正确用法是"用它来验证前五个模块好不好用"，而不是"再建一个系统"。**

如果做教程时发现 Part 5 的计划功能用不了，那是 **Part 5 该改**——这才是探索的价值。
