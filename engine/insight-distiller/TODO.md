## 20. 知识关联偶发 FOREIGN KEY constraint failed

**现象**：批量浓缩 10 期时有 1 期在知识关联阶段报
`FOREIGN KEY constraint failed`，重跑同一条无法复现。

**已排除**：
- `PRAGMA foreign_key_check` 通过，数据库无悬空引用
- claims / relations / entity_mentions / questions 全部完整
- 该条内容的 digest 与 claim 都正常写入
- 浓缩结果未受影响（被 `_try_link` 的 try 正确兜住）

**影响**：低。知识关联是增强功能，失败只是少了几条实体关系，
不影响问答卡片与导出。这也是当初把它包在 try 里的原因。

**排查方向**：偶发说明有竞态。可疑点是 `Linker` 在写 relations 时
引用了另一条正在被 upsert 的 source，或 entity 合并时并发写入。
建议在 `_try_link` 的 except 里打印完整 traceback（当前只打印 message），
下次复现能直接定位。

**性价比**：中。不影响主流程，但「偶发且看不到堆栈」这种问题
积累下来会很难查，值得先把 traceback 补上。

## 18–19. 批量导入可用性 ✅ 已实现

**来源**：抓「每天一个宝藏问题」全系列 211 期时踩到的一组坑。
共同点是**工具没坏，但用起来不可控**——我最后只能绕过 CLI
自己写脚本配 `nohup` + `tail` 日志才跑完。
批量导入是核心场景之一，需要绕过 CLI 才能完成，本身就说明能力缺失。

### 18. `--subtitle-only`

`--no-distill` 只关「浓缩」，不关「转写」。批量跑到无字幕视频时会静默
启动本地 Whisper：**CPU 482%、内存 4.3GB、单条数分钟**，
日志毫无提示，看起来就是卡死（我第一次直接误判成死循环 kill 了进程）。

```bash
distill add <url> --subtitle-only
distill find "..." --run --subtitle-only
```

两个配套设计：
- 新增 `SubtitleMissing` 异常（继承 `FetchError` 保持兼容），
  让「按预期跳过」与「真失败」**分开统计**——
  混在一起报「失败 30 条」会让人以为出了问题。
- 不加该参数时，转写前打印明确提示（含时长预估与 `--subtitle-only` 提示），
  不再让人猜为什么慢。

### 19. 批量过程可观测

| 改进 | 解决什么 |
|------|---------|
| `[i/N]` + **剩余时间估算** | 原来完全不知道还要多久（前 3 条不估，样本太少会误导） |
| 进度与标题**分两行** | 标题本就可能占满宽度，拼一起会折行反而看不清 |
| **失败清单**（URL + 原因） | 原来只报「失败 N 条」，不知道是哪些、为什么 |
| **Ctrl-C 优雅中断** | 报告已完成数与剩余数，并说明重跑同一指令即可续跑 |
| 总耗时 | 便于估算下次同类任务 |
| `find` 支持 `--no-distill` | 无 LLM 时也能批量入库（原来只有 `add` 有） |

续跑之所以安全：已完成的都已入库，重跑会自动跳过已消化的。

### 顺带修掉的静默截断

`qa-export --limit` 默认值是 200。导出 211 题的系列会**静默少 11 题**，
输出还显示「✓ 已导出 200 题」——这类「看起来成功」的截断最难发现。
改为默认不限量。

## 16. 平台采集器可配置化 ✅ 已实现

**原始需求**：「能导入的社交平台做成可配置的，这个设计现实吗？比如小红书，知乎，bilibili，抖音」

**结论：这个问题要拆成两层，答案完全不同。**

### 第一层：开关 + 参数配置 —— 现实，已实现

```yaml
ingest:
  platforms:
    xhs:
      enabled: true
      rate_limit_sec: 3.0          # 风控最严，必须限流
      cookies_from_browser: edge   # 可单独覆盖全局
    bilibili:
      enabled: true
      timeout: 90
```

```bash
distill platforms                              # 看各平台状态
distill platforms --test <url>                 # 测某链接走哪个采集器
```

**为什么这层确实需要**：平台之间风控强度差异很大，全局一套参数不够用。
小红书连续请求极易触发验证（必须限流），B 站不配 cookie 拿不到字幕，
普通网页什么都不需要。此前这些只能全局配，做不到按平台区分。

**一个关键设计决定**：禁用某平台后，该平台链接**明确报错而非降级到通用抽取**。
因为通用兜底器对所有 URL 都 `match`，不特殊处理的话禁用就变成了静默降级——
而小红书正文在嵌套 JSON、B 站正文在字幕接口，通用抽取只会拿到空内容或噪声。
**给用户残缺数据却不说原因，比直接报错危险得多。**
（这个 bug 在实现过程中真的出现了，已加回归测试守住）

### 第二层：用 YAML 声明一个新平台 —— 对这四个平台不现实

先看现有采集器实际在做什么：

| 采集器 | 行数 | 平台特有逻辑 | 能用选择器表达？ |
|--------|------|-------------|----------------|
| bilibili | 252 | **WBI 签名**（64 位混淆表 + 动态 key + md5）、cid 提取、字幕优先级排序（人工 > AI、中文优先）、碎句合并成段 | **否，这是算法不是参数** |
| xhs | 135 | `__INITIAL_STATE__` 提取 + 在嵌套 JSON 里**广度搜索**定位 note 节点（因为路径会变，不敢硬编码）、滑动验证检测 | **否** |
| zhihu | 115 | 私有 API `/api/v4/articles/{id}`、URL 模式区分文章/回答 | 部分 |
| wechat | 109 | `data-src` 懒加载、`rich_media_title`、OCR 触发判断 | 部分 |

**一句话总结：声明式解决「解析」，解决不了「拿到」。**
拿不到内容的平台，配一百个选择器也没用。

### 但第二层有个有价值的子集 —— 已实现

对「**正文在固定 DOM 节点**」的站点（个人博客、新闻站、文档站），
声明式配置完全可行且很有用：

```yaml
ingest:
  sites:
    - name: ruanyifeng
      match: ["ruanyifeng.com"]
      title: "h1#page-title"
      content: "div#main-content"
      remove: ["div.comments", "nav", "footer"]   # 先删噪声再抽正文
```

**为什么这个子集值得做**：这类站点在「通用网页」里占大多数，
而 trafilatura 的通用抽取对结构特殊的页面（带侧栏的文档站、
评论区很长的博客）经常抽进噪声。如果你常读某几个站点，
配个选择器能明显提升浓缩质量。

实现细节上有两点值得记：
- 优先级设 50（内置专用是 10，通用兜底是 100）——用户显式写的规则
  应当优先于通用抽取，但不该盖掉专用采集器。
- 逐个块级子节点取文本而非直接 `text_content()`，否则所有段落会被挤成一行，
  丢掉段落边界（浓缩时分块会受影响）。
- 同时支持 CSS 与 XPath（以 `/` 开头判定）。CSS 覆盖 95% 场景且大家都熟，
  但少数情况（按文本定位、取属性）只有 XPath 能表达。

### 代价

新增 `cssselect` 依赖（30KB 纯 Python，跨平台零风险）。
`lxml` 本来就随 trafilatura 进来了。

## 17. 抖音采集器

**原始需求**：（随 #16 一起提出）「比如小红书，知乎，bilibili，抖音」

**结论：不建议做。技术难度不是主要原因，产品定位才是。**

| 维度 | 评估 |
|------|------|
| **可行性** | **低**。反爬在国内平台里最严：请求签名（`X-Bogus`/`a_bogus`）+ 设备指纹 + 极短的 token 有效期。签名算法混淆在 JS 里且频繁变动，需要跑 JS 引擎或逆向，维护成本持续存在。且**没有公开字幕接口**，必须走 ASR |
| **必要性** | **低**，但原因不是技术 |
| **性价比** | **很低** |

**真正的问题在产品层面**：

这个工具的定位是「把**低信息密度**内容压缩成**高密度**结论」。
抖音的主体是 15~60 秒短视频——一个 30 秒视频转写出来大约 100~150 字，
浓缩后还不如原标题信息量大。**压缩没有意义，因为它本来就没有可压缩的冗余。**

换句话说：B 站一个 40 分钟的视频值得压成 5 条结论（这是真实价值）；
抖音一个 30 秒视频压成 1 条结论，等于什么都没做。

**如果确实要处理抖音内容**，现成的路径成本低得多：

```bash
# 抖音 app 里复制文案 → 粘贴
distill add "视频标题" --paste

# 或者下载视频文件后走本地转写（#1 已实现）
distill add ~/Downloads/douyin_video.mp4
```

**唯一值得重估的情况**：如果你主要看抖音上的长视频（知识类博主的
10 分钟以上内容），那压缩就有价值了。这种情况下建议先用
`yt-dlp`（已是依赖，它支持抖音）下载，再用 `distill add 文件路径`——
绕过签名问题，且复用已实现的转写链路。

这条路**现在就能用**，不需要开发。

## 1. 处理本地录音文件 ✅ 已实现

**原始需求**：「这个工具支持处理录音文件吗？」

**实现于 2026-09-17**。此前 `distill add 录音.m4a` 会报「没有可用的采集器」——
Whisper 引擎本就支持直接吃文件路径，缺的只是入口，而那个错误完全看不出真正原因。

现在支持：

```bash
distill add ~/录音.m4a       # 音频：mp3 m4a wav flac aac ogg opus wma aiff amr m4b
distill add ~/会议.mp4       # 视频：mp4 mkv mov avi flv webm ts m4v（自动抽音轨）
```

**为什么这条性价比极高**：引擎、VAD、时间戳锚点、分块、浓缩全都是现成的，
真正新增的只有「后缀识别 + ffmpeg 抽音轨 + 一个 RawContent 构造」，
约 110 行。而它解锁的是一整类输入源（会议录音、语音备忘录、下载的播客文件）。

**实现中的注意点**：
- 视频必须先抽音轨。Whisper 只认音频，直接喂视频会失败或极慢。
- URL 用路径哈希（`localmedia://<sha1>/文件名`）而非绝对路径 ——
  库内不存绝对路径是跨平台的硬约束，且哈希能让重复导入命中去重。
- 顺序很关键：**论文判断必须在「本地文件」之前**。本地 PDF 也是存在的文件，
  若先走文本读取会被当纯文本解析失败，而它本该走论文分节链路。
  （这个 bug 在实现过程中真的出现了）

**已知限制**：
- 1 小时录音在 CPU 上约 15~25 分钟，有 NVIDIA 显卡约 3~6 分钟。
- 首次需下载 Whisper 模型（large-v3 约 1.5GB）。
- 不做说话人分离（见 #6）。

## 3. 播客 RSS 订阅

**原始需求**（推测自「我平时看很多博客、视频网站」）：订阅播客后自动消化新单集。

| 维度 | 评估 |
|------|------|
| **可行性** | 高。RSS 解析是标准活，音频 URL 直接下载后复用现有转写链路 |
| **必要性** | 中高。播客信息密度普遍偏低、时长又长，正是这个工具最该解决的场景 |
| **性价比** | **高**。本地录音（#1）已打通「音频文件 → 转写 → 浓缩」，RSS 只需加「解析 feed + 下载 enclosure」 |
| **工作量** | 约 1 天。一个 `PodcastAdapter` + 复用 `subscribe` 的调度 |

**建议做法**：不引入 `feedparser`（多一个依赖），用 `httpx` + 标准库
`xml.etree` 解析即可——RSS 结构简单，只需取 `item/enclosure@url`、
`title`、`pubDate`、`itunes:duration`。

**注意**：单集常达 1~2 小时，CPU 转写要 30 分钟以上。
订阅场景必须设 `max_items`（现有机制已支持），否则一次更新 5 集就跑一整晚。

## 7. `find` 输出 JSON


## 8. 批量导入本地文件夹

**原始需求**：（推测）手头已有一堆录音 / PDF / 文本，想一次性入库。

| 维度 | 评估 |
|------|------|
| **可行性** | 高。遍历目录 + 复用 `add` 逻辑 |
| **必要性** | 中高。有历史积累时，一个个 `add` 很痛苦 |

**建议做法**：

```bash

```

**必须有的**：成本预演（一批录音的转写时间可能是几小时）、
逐条失败隔离（一个坏文件不该中断整批）、跳过已导入（复用 URL 哈希去重）。

| 维度 | 评估 |
|------|------|
| **可行性** | **低**。公众号没有公开的文章列表接口。可行路径都有明显缺陷：① 抓「搜狗微信」——只有最近 10 篇且限流严重；② 用自己的登录态调后台接口——需要公众号管理员权限；③ 客户端抓包——脆弱且违反使用条款 |
| **必要性** | 中。确实是真实需求 |
| **性价比** | **低**。实现脆弱、随时可能失效，维护成本高 |

**结论：暂不做。** 建议的替代方案是：在微信里把想读的文章「转发到文件传输助手」，
然后逐条 `add`。或者用 RSS 服务（如 RSSHub）把公众号转成 feed，
等 #3 的 RSS 能力做好后就能直接订阅。

## 10. 微信读书 / Kindle 笔记导入

**原始需求**：（推测）读书划线与笔记也是高价值内容源。

| 维度 | 评估 |
|------|------|
| **可行性** | 中。Kindle 的 `My Clippings.txt` 是纯文本，格式固定好解析；微信读书需要导出（有第三方工具） |
| **必要性** | 中。书籍笔记的信息密度通常高于视频，且**你自己划过线**说明已筛选过一轮 |
| **性价比** | **中**。Kindle 部分约半天（纯文本解析）；微信读书依赖第三方导出，不可控 |

**建议**：先只做 Kindle `My Clippings.txt`——格式稳定、零依赖。
每条划线带书名与位置，正好映射到现有的 `Segment.section` 锚点。

## 13. 浓缩结果人工修正并反馈

**原始需求**：（推测）LLM 浓缩偶尔会漏重点或理解错，想手动改。

| 维度 | 评估 |
|------|------|
| **可行性** | 高。`digests` 表已有 `schema_version` / `prompt_version`，加一条「用户修正版」不难 |
| **必要性** | 中高。**改错不只是修这一篇**——积累的修正样本能反过来改进 prompt |
| **性价比** | **中高**。基础版（网页版里直接编辑 TL;DR 并保存）约 1 天 |

**建议做法**：
- 修正版另存而非覆盖原始输出——保留原始才能对比 prompt 迭代效果。
- 网页版阅读页直接可编辑（已有批注机制，扩展成可编辑浓缩结果）。
- 长期价值在于：攒够修正样本后，能看出 prompt 在哪类内容上系统性出错。

## 14. 视频关键帧截图

**原始需求**：（推测）技术教程、图表讲解类视频，纯文字丢失关键信息。

| 维度 | 评估 |
|------|------|
| **可行性** | 中。ffmpeg 按时间戳抽帧很简单；难的是**判断哪一帧值得抽** |
| **必要性** | 中。看教程/评测类内容时，一张图胜过一段描述 |
| **性价比** | **中**。抽帧容易，选帧难。若按固定间隔抽会产生大量无用图片 |

**建议做法**：只在「大纲锚点」处抽帧（每个小节一张），而非全片扫描。
这样数量可控（一个视频 5~10 张），且正好对应内容结构。
Obsidian 导出时嵌入图片，阅读体验提升明显。

## 附：已知的小缺口

这些不算需求，是实测中发现但优先级不高的问题。

| 问题 | 影响 | 建议 |
|------|------|------|
| 纯 arXiv 编号（`2310.06825`）不被识别为论文 | 需用完整链接或 DOI | 加个正则即可，10 行 |
| B 站字幕需登录态 | 未配 cookie 时全部走转写，成本高 50 倍 | 已在手册说明；可考虑首次运行时主动提示 |
| `find` 的候选无法按时长/密度预筛 | 只能靠 `--exclude` 报序号 | 与 #7 一起做 |
| 发现阶段不探测字幕 | 成本预演只能给上限 | 探测要为每条候选多发一次请求，当前的「上限估算 + 明确标注」是合理折中 |
| Whisper 模型首次下载慢 | 国内网络体验差 | 已在手册给出 `HF_ENDPOINT` 镜像方案；打包时可用 `--with-models` 带走 |
