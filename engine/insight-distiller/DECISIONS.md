# 决策记录（ADR）

## 2026-09-16 · 选型确认

| 项 | 决定 | 备注 |
|----|------|------|
| LLM 路线 | **全面可配置**，按任务粒度指定 provider | 见 `config.example.yaml` 的 `tasks` 与 `profiles` |
| 默认 API | **DeepSeek**（`deepseek-chat` / `deepseek-reasoner`） | 可切 OpenAI / Claude / Kimi / Ollama |
| 内容来源 | **B 站、小红书** + **中文博客、公众号、知乎** | M1 先做 B 站 + 通用网页（含公众号），M2 补小红书 |
| 交互形态 | **CLI 先行** | 网页版留到 M3 |

### 关键推论
1. 来源全是**中文内容**，因此：
   - ASR 用 `large-v3` 而非 `medium`（中文小模型错字率高很多）。
   - Embedding 用 `bge-m3`（中文语义检索显著优于 OpenAI embedding）。
   - 摘要输出语言固定中文，无需翻译链路。
2. 小红书 / 知乎 / 公众号都有反爬或登录墙 → `cookies_from_browser` 必须做，且要有「手动粘贴」兜底，不能让采集失败阻断主流程。
3. 公众号大量文章是**图片承载正文** → OCR 不是可选项而是必需项；macOS 原生 Vision（`ocrmac`）无需下载模型且中文识别准确率高，优于 PaddleOCR 的部署成本。

## 2026-09-16 · 追加：输入形态扩展为自然语言选材

**需求**：输入不限于单个 URL，支持"某博主美食方向"、"某专栏收藏量前 100"这类自然语言指令；工具自行判断，不合理时反问澄清。

**决定**：新增独立的 Discovery 层，完整设计见 `DISCOVERY.md`。里程碑插入为 **M2.5**（不拖慢 M1 出可用版本）。

### 关键设计取舍
| 问题 | 决定 | 理由 |
|------|------|------|
| 反问的尺度 | **只在"猜错代价高"时阻断**：实体不唯一、语义真歧义、量级超预算、指令明显不合理。其余情况自行决定但必须在 `assumptions` 里显式声明 | 动辄反问极其影响体验；但静默默认又会烧掉大量算力。折中点是"自动决定 + 全部可见" |
| 反问形式 | 结构化选项（数字选择），非开放式对话 | 减少来回轮次 |
| 执行前 | `find` 默认**只发现不消化**，先出候选表 + 成本预演，确认后才跑 | 防止一句话烧掉两小时 ASR 算力 |
| 主题方向判定 | 两阶段漏斗：元数据/关键词/embedding 免费粗筛（约 80%）→ 仅边缘案例交 LLM 批量判定 | 对几百条候选逐个跑 LLM 太慢太贵，成本可压到 1/10 |
| 平台能力不足 | 本地补偿并**明示口径**（如"基于播放量 Top300 候选池的近似收藏量 Top100"） | 不伪装精确 |

### 踩到的平台现实约束
- **B 站不支持按收藏量检索**（空间搜索仅播放量/日期），且投稿列表接口不返回收藏数 → 必须"拉大候选池 + 逐条补 stat + 本地重排"，并配限流与缓存。接口还需 WBI 签名且规则会变 → 签名逻辑单文件隔离 + `distill doctor` 自检。
- **公众号没有公开的"某号全部文章"接口** → 历史文章只能靠 RSS 中转或手动导出，这是硬限制，方案里不做过度承诺。
- **知乎列表接口直接返回 `voteup_count` / `favorite_count`** → 是最容易实现精确排序的平台，所以"专栏收藏量前 100"这类需求优先在知乎落地。
- **小红书风控最强** → 降级为 P2，优先支持"导出收藏夹再批量消化"而非在线抓取。

### 一个必须反问的典型例子
"某专栏收藏量前 100" 存在真歧义：①该专栏文章按**被收藏数**排序前 100 ②**我的收藏夹**里的前 100 篇。两者结果完全不同，必须问清。

## 2026-09-16 · 追加：学术论文模块 + 知识管理层

**需求**：① 丢一篇论文，找相似/相近论文；② 建知识管理系统，便于重温，且新丢的 URL/论文若与历史内容有关联要能发现。

**决定**：新增两个模块，见 `PAPERS.md` 与 `KNOWLEDGE.md`。里程碑重排为 M1 → M2 → M2.5 → **M3 论文** → **M3.5 知识关联** → **M4 重温** → M5 Web UI → M6 自动化。

### 关键设计取舍

| 问题 | 决定 | 理由 |
|------|------|------|
| 论文能否复用视频链路 | **不能，独立解析器 + 独立 schema** | 论文有固定章节结构，关键信息是方法/实验/局限，且引文关系是比语义更强的相似信号 |
| 相似论文如何找 | **四路召回 + RRF 融合**：S2 推荐 / 引文图谱（含共被引、文献耦合）/ SPECTER2 向量 / 概念作者检索 | 单一策略都有盲区：协同过滤对冷门论文失效，引文对新论文失效，向量会召回"表面像"。共被引是几十年验证的可靠指标 |
| 推荐结果如何呈现 | **分组**（奠基工作 / 同期竞品 / 后续进展 / 跨领域启发）+ 标注是否已在库中 | 平铺列表无法体现学术脉络；「跨领域启发」组只有向量能发现，是新想法来源 |
| 知识管理靠什么驱动 | **入库即自动关联**，不依赖用户手动打标签/双链 | 手动整理成本高到必然放弃，这是所有笔记工具沦为"写入即遗忘"的根因 |
| 关系是否要分类型 | **必须分**：cites / contradicts / supports / extends / prerequisite / answers / duplicate | 只标记"相关"没有决策价值。`contradicts` 价值最高——认知升级多来自发现矛盾 |
| 冲突检测的边界 | 只在双方都有明确结论句时判定，**必须附双方原文证据，只提示不裁决** | 避免 LLM 武断判定对错 |
| 关联的成本如何控 | **三级漏斗**：引文 API（免费确定）→ 向量召回 Top20（本地零成本）→ 仅 Top5 交 LLM 批量判定 | 每篇新内容仅增约 1 次 LLM 调用（¥0.003），**成本不随库规模增长**，这是关键 |
| 是否引入图数据库 | **不引入**，SQLite 递归 CTE 足够 | 个人场景关系边最多几万条，Neo4j 是过度设计且增加运维 |
| 重温机制形态 | **轻量唤醒**（只推 TL;DR + 自己的批注），非 Anki 式记忆卡；默认只对密度 > 60 或标星内容排期 | 严格记忆卡对成年人技术学习负担过重，容易放弃；且不能被水文淹没 |
| schema 何时定 | **M1 就落全**（含 entities / relations / questions / reviews） | 留到 M3.5 再加会触发数据迁移，代价远高于提前设计 |

### 实测确认的外部 API 约束（2026-09）
- **Semantic Scholar**：有专门的 Recommendations 接口（相似论文主力）。但无 key 时 1000 req/s 是**所有匿名用户共享**（实际频繁 429），**有 key 反而只有 1 req/s 入门限额** → 必须本地缓存 30 天 + 指数退避 + 降级到 OpenAlex。
- **OpenAlex**：无需 API key，积分制，免费每日 10 万积分（列表请求 10 分 → 约 1 万次列表查询/天），每秒上限 100 次。加 `mailto=` 进 polite pool 响应更稳。**支持 OR 语法一次合并最多 50 个 ID**，批量补元数据时请求数降到 1/50，是省额度的关键手段。
- 因此分工：**元数据与引文图谱走 OpenAlex（额度充裕），相似推荐才用 S2（重缓存）**。
- **中文论文（知网/万方）覆盖差**，是硬限制，靠本地 PDF 导入兜底，不做过度承诺。

### 论文 embedding 单独选型
通用 `bge-m3` 用于中文内容检索，但论文相似度改用 **SPECTER2**（专为学术论文训练，在标题+摘要相似任务上远优于通用模型）。即两套 embedding 并存，按 `content_type` 分流。

## 2026-09-16 · 追加：Agent 友好（面向理财 agent 等外部消费方）

**需求**：知识库要对 AI Agent 友好，方便后续自己开发的理财 agent 调用。

**决定**：新增 Agent 接口层，见 `AGENT_API.md`。核心不是"加个 API"，而是**改变知识的对外形态**。里程碑定为 **M6**（依赖 claims 与 domain 就绪）。

### 核心判断
**给人看的散文摘要，和给 agent 用的知识，是两种产物。** 若只把摘要文本通过 API 抛给 agent，agent 拿到的是"没有出处、没有时效、不分事实与观点"的裸结论——对理财场景是有害输入。

### 关键设计取舍

| 问题 | 决定 | 理由 |
|------|------|------|
| 对外知识的粒度 | 新增 **Claim 原子知识单元**（`claims` 表），而非整篇摘要 | agent 需要精确引用一条主张并程序化处理，文档级粒度太粗 |
| 是否区分知识性质 | **必须**：`claim_type` ∈ fact / opinion / prediction / method / data | 理财内容里事实与自媒体观点高度混杂，不区分则 agent 必然把观点当事实 |
| 时效如何处理 | 每条 claim 带 `as_of` + `expires_hint`，返回时**强制携带 `staleness_days`**，检索按时间降权 | 金融知识会过期（利率、政策、税率），这是与技术知识最大区别；2024 年的利率判断放到 2026 年是错的 |
| 数字如何给 agent | 抽取为 `numeric_json` 结构化字段 | 让 agent 直接参与计算，避免 LLM 从散文里二次解析数字（极易出错） |
| 观点冲突如何呈现 | **不做合并**，`kb_get_claims` 强制分组为共识 / 分歧 / 存疑 | 把分歧平均成"中立结论"会掩盖关键信息；理财观点冲突极多，分歧本身就是决策依据 |
| 如何防止 agent 误用 | 在 **outputSchema 的 `required`** 里强制包含 `staleness_days` / `authority` / `citation` | 从 schema 层面杜绝拿到裸结论，比在文档里写注意事项有效得多 |
| 库内无知识时 | 返回 `coverage.sufficiency = empty` + `warnings` | 让 agent 明确降级说"知识库无依据"，而不是硬编答案 |
| 多领域混杂 | `domain` 分区，向量库按 domain 建**独立 collection** 物理隔离 | 理财 agent 不该被摄影内容干扰；同时提升精度与速度 |
| 接入协议 | **MCP 为首选**，HTTP API 与 Python SDK 并行提供 | MCP 2026-07-28 规范支持 `outputSchema` + `structuredContent`，服务端 MUST 返回符合 schema 的结构化结果，天然满足强类型知识需求 |
| 两通道契约一致性 | MCP 与 HTTP **共用同一套 Pydantic 模型**生成 schema | 避免两边定义漂移 |
| 上下文预算 | 提供 `token_budget` 入参，由知识库按预算裁剪并保留高价值 claim | 比让 agent 自己截断字符串合理 |
| 是否提供投资建议接口 | **不提供**。工具只回答"你库里有谁说过什么、何时说的、可信度如何" | 既是合规边界，也是工程正确性——把预测当事实用是投研里最常见的亏钱方式 |

### MCP 规范实测确认（2026-07-28 版）
- 版本号为日期式 `2026-07-28`；消息格式 JSON-RPC 2.0；本版强调**无状态、自包含请求**与**按请求能力协商**。
- 三大原语定位：**Resources = 读数据（面向用户/模型）、Prompts = 用户选模板、Tools = 模型执行动作**。本方案的知识查询主要走 Tools（模型主动调用），部分静态内容可作 Resources。
- `outputSchema` 为可选字段，默认 JSON Schema 2020-12 方言；**一旦声明，服务端 MUST 返回符合该 schema 的结构化结果**，客户端 SHOULD 校验 → 正是我们需要的强约束。
- `structuredContent` 可为任意 JSON 值；为向后兼容，**SHOULD 同时在 `content` 中放一个 text 块**（序列化 JSON 或人类可读摘要）。
- `tools/list` 结果 **MUST NOT** 随连接变化，SHOULD 返回确定性顺序（利于缓存与 prompt cache 命中）；本版新增 `ttlMs` / `cacheScope` / `nextCursor`。
- Tool annotations **客户端必须视为不可信**（除来自可信服务端）→ 因此只读性不能只靠声明，服务端侧必须真正只读。
- **Tasks 扩展**支持长时异步操作与持久化句柄 → 视频消化耗时数分钟，`kb_ingest` 走 Tasks 而非同步调用。
- 有状态操作需通过显式 handle 传递（协议无 session 概念）。

### 抽取成本控制
Claim 抽取不额外增加一轮 LLM 调用：在原 map-reduce 的 **map 阶段顺带输出 claim 草稿**；仅对已配置 domain 且密度达标的内容抽取（水文无可用 claim）；支持事后 `distill claims extract` 批量补抽；数字与日期用规则+正则**后处理校验，抽错即丢弃**而非将错就错。

### 安全记录
调研 MCP 官方文档时，页面内嵌了一条指挥 AI 抓取 `/llms.txt` 索引文件的指令（prompt injection 模式）。未执行该指令，仅按自身判断抓取了所需的 Tools 子页面。后续开发涉及抓取外部网页内容送入 LLM 时，需注意同类风险——**采集到的正文不应被当作指令执行**，这一点要写进 prompt 隔离策略。

## 2026-09-16 · 追加：跨平台迁移（Windows）与可迭代性约束

**需求**：方案要适合后续迭代，并能迁移到 Windows。

**决定**：新增 `PORTABILITY.md`；平台差异全部收敛到 `src/distiller/compat/` 单一目录，业务代码禁止出现平台判断。

### 因跨平台而**修订的既有选型**（重要）
| 原选型 | 修订为 | 原因 |
|--------|--------|------|
| OCR 用 `ocrmac`（Apple Vision） | **默认 `RapidOCR`**，ocrmac 降为 macOS 可选加速 | Windows 无 Apple Vision。更关键的是：若两端 OCR 引擎不同，迁移后会出现"摘要质量变了"这类极难排查的问题，因此**默认实现必须是跨平台的那个** |
| ffmpeg 靠 brew 安装 | **`imageio-ffmpeg` 自带二进制** | 本机无 brew；Windows 安装方式完全不同；该包提供三平台预编译二进制，pip 即得 |
| 依赖管理用 `uv` | **标准 `venv` + `pip`**（pyproject 仍兼容 uv） | uv 需额外安装步骤且本次安装未获授权；venv/pip 是 Python 标准工具，两端行为一致 |
| ASR 默认 engine 未明确 | **`faster-whisper` 为基准**，`mlx-whisper` 仅 macOS 可选 | 基准实现必须跨平台，否则迁移等于重写 |
| 数据目录位置随意 | **项目内 `./data`，且库内只存相对路径** | 整个项目文件夹可直接拷到 Windows，数据零转换 |
| 未考虑文件编码 | **强制 UTF-8 IO 封装，禁止裸 `open()`** | Windows 默认 ANSI（中文环境 cp936），全中文内容必然乱码 |
| 包名拟用 `platform/` | 改为 **`compat/`** | 避免与 Python 标准库 `platform` 模块混淆 |

### 环境实况（与原计划的偏差）
- 本机无 brew，`uv` 安装脚本未获授权 → 改用 `venv + pip`，反而更贴合"零额外系统依赖"的迁移目标。
- 实际装到 **Python 3.14.3**（非计划的 3.12）。已验证 `trafilatura 2.2.0` / `lxml` / `pydantic` / `typer` 均有可用 wheel，无需编译。
- M1 不需要 ffmpeg（无音视频转写），已列为可选依赖组 `[av]`，装不上不影响 M1 可用。

## 2026-09-16 · M1 开发中发现并修复的缺陷（记录以防复发）

这些都是**实现阶段才暴露、方案层面看不出来**的问题：

| # | 缺陷 | 影响 | 修复 |
|---|------|------|------|
| 1 | **分块去重用 `text[:200]` 作键** | **严重：静默丢失原文。** 测试中 20 段内容只产出 1 个 chunk，18 段被丢弃。真实触发场景：重复开场白、结构化列表、模板化段落 | 改用 `segment_idxs` 作为去重键（去重本意只是消除 overlap 产生的重复块）。已加回归测试断言「所有片段必须被覆盖」 |
| 2 | **密度评分的逻辑连接词表只有中文** | 英文内容「论证结构」项恒为 0，密度被系统性低估约 20 分 | 补充英文逻辑连接词与口水词表，中英分别统计 |
| 3 | **句子切分正则不含英文句号** | 英文长段落被当成单个句子，「有效句占比」虚高、「重复率」失真，中英文评分标准不一致 | 改为 `[。！？；;\n]+\|(?<=[.!?])\s+`：中文标点直接切，英文 `.!?` 需后跟空白才切，从而不误切 `3.14` 这类小数（已加测试） |
| 4 | **有效句阈值中英统一为 15 字符** | 英文 15 字符仅约 3 个词，判定过松 | 按语言自适应：中文 15、英文 40 |
| 5 | **`usable` 假设「除 ollama 外都需 API Key」** | 误伤本地部署的 vLLM / LM Studio 等无需认证的 OpenAI 兼容端点，以及任何自定义 provider | 仅对 `openai_compat` / `anthropic` 强校验，且 base_url 指向 localhost 时视为无需认证 |
| 6 | **rich 把 `[ocr]` 当 markup 标签吞掉** | 提示信息显示为 `pip install -e '.'`，**用户会照着错误命令执行** | 所有含外部数据/方括号的输出统一 `rich.markup.escape()`，包括标题与 LLM 生成的结论 |

**结论性经验**：第 1 条这类"静默丢数据"的 bug 不写测试是发现不了的——它不报错，只是结果变差。因此 `chunker` / `density` / `safe_filename` / 相对路径这几个纯函数必须有测试守护，且 CI 要在 macOS 与 Windows 双平台跑。

### M1 交付验证
- 24 项测试全通过，其中用 fake LLM provider 覆盖完整 map-reduce 链路，**LLM 相关代码已实际执行**，不依赖真实 API Key。
- 真实端到端跑通：采集 Lilian Weng 的 agent 综述（38746 字 / 254 段 → 6 chunk）→ 浓缩 → 入库 → 导出 Markdown。
- 水文识别可靠：中文与英文口播水文均评 0 分；技术长文 56–62 分。

## 2026-09-16 · M2 完成：音视频转写 + 混合检索问答

### 依赖实测（Python 3.14）
全部可用，无需降级 Python：`faster-whisper 1.2.1` / `lancedb 0.38.0` / `torch 2.14.0` / `sentence-transformers 6.0.1`。

### 关键设计取舍

| 问题 | 决定 | 理由 |
|------|------|------|
| 向量存储用什么 | **SQLite BLOB + numpy 计算**，LanceDB 降为可选后端 | M2 的价值是"能问答"，不是"用哪个向量库"。个人规模（数万块）下 numpy 点积毫秒级完成，且**零额外依赖、跨平台零风险**。LanceDB 会拉入 pyarrow 等重依赖，规模大时再切（接口不变） |
| 融合策略 | **RRF（按排名倒数融合）** 而非分数加权 | 余弦相似度与 BM25 分数量纲不可比，加权需要调参且不稳定；RRF 无参数、更稳健 |
| 是否上 rerank | **暂不上**，接口预留 | 双路召回 + RRF 已能满足；rerank 需再下一个模型（约 1GB）且增加延迟，等实际发现引用不准再加 |
| embedding 默认模型 | **`bge-small-zh-v1.5`（约 100MB）** 而非 `bge-m3`（2.2GB） | 首次使用要下载，2.2GB 会让用户以为卡死。小模型已能可靠区分语义（实测相关 0.469 vs 无关 0.315），需要更强效果时改配置即可 |
| 检索块大小 | **600 字符**（浓缩用 2000） | 检索块小则引用定位更精确；浓缩块大则上下文更完整。两者用途不同，不应共用同一尺寸 |
| 中文 FTS 分词 | **长词切二元组**后再 OR 连接 | SQLite `unicode61` 分词器对中文按单字切，长词直接查命中率极低 |
| bge query 前缀 | 检索时**自动加指令前缀** | bge 系列在检索任务上要求 query 侧加前缀，不加会明显掉召回。这是易被忽略的细节 |
| 无正文时的行为 | **明确失败 + 给出可执行建议**，不入库 | 让浓缩层拿到空内容会抛难懂的异常，或产出空摘要却让用户以为消化成功 |

### M2 开发中发现并修复的缺陷

### 关键设计取舍

| 问题 | 决定 | 理由 |

## 2026-09-16 · ⚠ 重大修订：学术 API 现状与原方案不符

**实测发现，`PAPERS.md` 里基于早期文档的选型必须推翻。**

### OpenAlex 已改为付费额度制（推翻「元数据主力」定位）
实测返回：
```
429 {"error":"Rate limit exceeded","message":"Insufficient budget.
This request costs $0.001 but you only have $0 remaining.
Resets at midnight UTC. Need more? Add funds at https://openalex.org/pricing"}
```
- 单篇 `works/{id}` 查询**可用**（曾成功取到标题、引用数、54 条参考文献、10 条 related_works、概念标签）。
- 但 **list / search 类请求（按 DOI 过滤、标题搜索、被引查询）全部被 429 拒绝**，当前 IP 预算为 $0。
- 原方案写的「免费每日 10 万积分、OR 语法合并 50 ID」已不成立。

### Semantic Scholar 匿名池同样受限，但引文端点可用
- `/recommendations` **稳定返回空列表**（多种 ID 格式均如此）→ **四路召回的「协同过滤」一路实际不可用**。
- `/paper/{id}/references` 与 `/citations` **可用**（实测各拿到 5 条真实数据），但需**指数退避重试**；单篇详情端点不稳定。
- 结论：S2 作为**引文图谱主力**，而非推荐主力。

### arXiv 必须用 HTTPS
`http://export.arxiv.org` 返回 **301**，导致解析全空。改用 `https://` + `follow_redirects` 后完全正常（标题、摘要 1136 字、8 位作者、发布日期均正确）。**arXiv 是当前最稳定的数据源，无限流问题。**

### 因此 M3 的修订方案

| 原计划 | 修订为 | 理由 |
|--------|--------|------|
| OpenAlex 作元数据主力 | **arXiv 作主力**，OpenAlex 仅用单篇查询做补充（可用时） | OpenAlex list 类请求已需付费 |
| S2 Recommendations 作相似推荐一路 | **移除该路**，改为四路：引文图谱（refs/citations）+ 共被引/文献耦合 + 语义向量 + 关键词/作者 | 该接口稳定返回空，保留只会误导用户 |
| 四路召回 | **仍是四路**，但换掉最不可靠的一路 | 引文关系本就是比协同过滤更可靠的学术相似度信号 |
| 未强调重试 | **所有学术 API 强制指数退避 + 30 天缓存 + 降级链** | 匿名共享池必然遇限流；论文引文关系变化极慢，缓存收益极高 |

**关键设计原则**：任何一路召回失败都不能让 `paper similar` 整体失败，必须降级并**明确告知哪一路不可用**，而不是静默返回残缺结果。

### M3 开发中发现并修复的缺陷

## 2026-09-16 · M3.5 完成：知识关联

**M1 预留的表全部派上用场，本次零 schema 迁移**——提前设计的收益在此体现。

### 关键设计取舍

| 问题 | 决定 | 理由 |
|------|------|------|
| 关联如何驱动 | **入库即自动关联**，不依赖用户手动打标签 | 手动整理成本高到必然放弃，这是笔记工具沦为「写入即遗忘」的根因 |
| 成本如何控制 | **三级漏斗**：引文+实体共现（纯 SQL 零成本）→ 向量召回 Top20（本地零成本）→ 仅 Top5 交 LLM 一次批量判定 | 每篇新内容约 1 次 LLM 调用，**成本不随库规模增长**。实测两篇内容仅 1 次判定调用 |
| 实体抽取是否额外调 LLM | **不额外调用**，复用 map/reduce 已产出的 `concepts` 字段 + 规则层补技术术语 | 实体抽取本身不值得单独花一轮调用 |
| 关系是否分类型 | **必须分** 8 种：cites/contradicts/supports/extends/prerequisite/answers/duplicate/same_topic | 只标「相关」没有决策价值；`contradicts` 价值最高 |
| 冲突如何处理 | **只提示不裁决**，必须附双方原文主张；缺证据的冲突判定自动降级为 same_topic | 避免 LLM 武断判定对错，让用户自己判断 |
| claim 数字如何保证 | **规则校验：数字未出现在原文即丢弃整条 claim** | agent 会拿这些数去计算，编造数值是最危险的错误。实测成功拦下伪造的「99.9%」 |
| 时间标注策略 | 格式不合法则丢弃而非猜测；领域要求时间但缺失时降置信度而非丢弃 | 猜错时间会让 agent 用过期知识；但完全丢弃有效 claim 又太浪费 |
| 是否引入图数据库 | **不引入**，SQLite 递归 CTE 足够 | 个人场景关系边最多几万条，实测多跳遍历距离计算正确且能防环 |
| 噪音如何控制 | 只展示 confidence ≥ 0.7 且每篇上限 5 条；用户可否决（`verified_by_user`），被否决的不再展示 | 关联提示过多会变成骚扰 |

### M3.5 开发中发现并修复的缺陷

| # | 缺陷 | 影响 | 修复 |
|---|------|------|------|
| 1 | **实体变体未合并**（`BERT` 与 `BERT-Large`、`GPT` 与 `GPT-3` 各占一条） | 实体表充满近似重复项，跨内容关联被稀释 | 识别版本后缀（`-large`/`-3`/`-base`/`v2`）并保留更具体的那个；同时确保 `bert` vs `roberta`、`rag` vs `ragtime` 不被误合并 |
| 2 | **实体名长度阈值过宽**（35 字的句子片段通过校验） | 句子片段被当作实体入库 | 按语言分别限制：中文 ≤14 字、英文 ≤4 词；含句末标点直接拒绝 |
| 3 | **领域判定单个关键词即命中** | 「今天聊聊摄影之外的话题」被判为摄影领域 —— **误归类会让 agent 检索到不相关内容** | 要求至少 2 个不同关键词命中；实测「量化投资+Python+利率+模型」正确识别为 finance+tech 双领域 |
| 4 | `_link_citations` 残留废弃的 `if False else` 条件表达式 | 死代码，可读性差 | 清理 |
| 5 | 配置文件存在顶层 `domains` 与 `knowledge.domains` 两处领域配置 | 用户不知道该改哪个，且顶层的实际不生效 | 删除顶层段，统一到 `knowledge.domains` |

**经验**：第 3 条这类阈值问题只有用「反例」测试才能发现——正例（真正的摄影内容）永远能通过。测试里必须包含「不该命中」的用例。

### 交付验证
- **178 项测试全通过，0.37 秒完成**（新增 39 项，含 5 条回归测试）。
- 真实端到端：消化两篇结论对立的内容 → 自动发现 `contradicts` 关系并附双方原文主张；实体 `BM25` 正确覆盖 2 篇内容（跨内容对齐成功）。
- **编造数字被拦下**：故意让 fake LLM 输出原文不存在的「99.9%」，规则校验提示「1 条 claim 因数字与原文不符已丢弃」。
- claim 正确分类为 fact/data/opinion，`timeline` 用 `as_of`（主张时间）而非发布时间排序。
- 成本控制验证：实体共现与语义召回均标注「零成本」，全流程仅 1 次 LLM 关系判定调用。
- 密度门槛生效：密度 34.9 的内容跳过 claim 抽取（阈值 35）。

## 2026-09-16 · M4 完成：重温与沉淀

**又是零 schema 迁移**——M1 预留的 `reviews` / `notes` / `questions` 表全部直接可用。

### 核心判断：传统 SRS 不能直接套用到知识内容

Anki 那套是为「记忆卡片」设计的——每张卡都该记住。但知识内容不是：
水文不值得重温，纯资讯看完就过期。**全部入队只会让重温变成负担，最后必然放弃**
（这是所有 PKM 工具的通病）。

因此入队要筛选，按「还有未完成的事」而非「时间到了」来驱动：

| 信号 | 权重理由 |
|------|----------|
| 有可执行项 | 最高——因为你还没做 |
| 有未解疑问 | 可能已经能回答了 |
| 被 ≥2 篇关联 | 是知识网络枢纽 |
| 密度 ≥ 65 | 值得反复看 |
| 用户 star | 绕过所有判断 |

### 其他关键取舍

| 问题 | 决定 | 理由 |
|------|------|------|
| 反馈档位 | **只留三档**（forgot/ok/easy） | 五档以上用户会纠结选哪个；对知识内容来说三档足够驱动间隔调整 |
| 间隔算法 | **简化 SM-2**，不上 FSRS | FSRS 需要大量历史数据训练，个人库数据量根本不够 |
| forgot 后间隔 | **重置到 2 天**而非 1 天 | 知识内容不像单词卡，隔天再看意义不大 |
| 间隔上限 | **365 天** | 避免算出「3 年后重温」这种无意义结果 |
| 重温展示什么 | **只展示 TL;DR + 待办 + 我的批注**，不展示全文 | 重温目的是唤起记忆并检查待办，不是重读一遍 |
| 简报是否调 LLM | **完全不调** | 这些都能从库里直接算出；每周例行任务不该产生 API 成本 |
| 简报内容 | 不罗列「这周看了什么」，而是**冲突/悬置待办/疑问闭环/盲区** | 清单看一次就够；有价值的是「你想不起来但工具记得」的东西 |
| Obsidian 导出 | 关系与概念都转 `[[双链]]`，可执行项转 checkbox | 直接复用 Obsidian 图谱视图，不必自己写可视化；也让知识能脱离本工具存在 |
| 概念页门槛 | 只导出跨内容出现的概念 | 单次提及的概念页没有连接价值 |

### M4 开发中发现并修复的缺陷

| # | 缺陷 | 影响 | 修复 |
|---|------|------|------|
| 1 | `sources_since` 查了 `digests.density_score` | **SQL 报错，简报完全不可用**。密度分只在 `sources` 表上，digests 里在 payload 内 | 改查 sources 表 |
| 2 | `sources` 表无 `char_count` 列 | 同上，简报崩溃 | 从 segments 聚合 `SUM(LENGTH(text))`；刻意不在 sources 冗余存储，避免与实际内容不一致 |
| 3 | 调用了不存在的 `db.monthly_cost()` | 同上 | 实际方法名是 `month_cost` |
| 4 | **重温展示的理由自相矛盾** | 已在队列的项显示「密度 42 偏低，不值得重温」——但它明明还在队列里。原因是展示时重新跑了入队判定，而阈值可能已被调高 | 拆出 `_display_reasons`：已入队的项说明「为何值得看」，不重新判定是否该入队 |
| 5 | **相同待办重复列出** | 两篇内容都产出「补上 BM25 分支」，简报里出现两次，稀释真正待处理的事项 | 按归一化文本去重（忽略标点空白）；`done` 批注也用同一键匹配 |
| 6 | **rich markup 吃掉批注类型标签** | `[insight]` 被当作 markup 标签，显示为空 | 用 `escape()` 转义 |
| 7 | 相同疑问重复展示 | 不同内容留下相同疑问时列多次 | `open_questions` 按文本去重（取最早那条） |

**经验**：第 1–3 条都是「凭记忆写 SQL 列名」导致的，三个连续报错才全部暴露。
教训是新增跨表查询时应先确认实际 schema，而非依赖对表结构的印象。

## 2026-09-16 · M6 完成：Agent 接口 + 订阅自动化（全部里程碑收尾）

### 核心判断：agent 友好的关键不是协议，而是知识的形态

假设理财 agent 问「该不该买长债」。如果知识库只返回摘要文本，
agent 拿到的是**有害**输入：不知道谁说的、什么时候说的、库里有没有相反观点。

所以强制每条 claim 携带这些字段，并在 Pydantic schema 里设为 `required`：

| 字段 | 防的失败模式 |
|------|-------------|
| `claim_type` | 不区分 fact/opinion/prediction，agent 必然把自媒体观点当事实 |
| `staleness_days` | 金融知识会过期，2024 年的利率判断放到 2026 年是错的 |
| `authority` | 官方公告与自媒体不该等权 |
| `citation` | 无出处的结论无法核实 |
| `coverage.sufficiency` | 库里没知识时返回 `empty`，agent 才知道该说「我没有依据」 |

**在类型层面约束比在文档里写注意事项有效得多** —— agent 拿不到裸结论，
因为构造 `Claim` 时缺 `citation` 会直接 ValidationError。

### 契约同源：三通道物理上不可能漂移

MCP / HTTP / SDK 都指向 `agent/schemas.py` 的同一批 Pydantic 类。
意外收获：新版 MCP SDK 从**函数返回类型注解**自动生成 outputSchema，
所以只要把返回类型标成 `SearchResponse`，MCP 的 schema 就是那个类本身——
比手写 JSON Schema 可靠得多。实测 `kb_search` 的 outputSchema 里
`Claim.required` 精确包含 `authority`/`citation`/`staleness_days`。

### 其他关键取舍

| 问题 | 决定 | 理由 |
|------|------|------|
| 时效处理 | **降权而非硬过滤**，但强制返回 `staleness_days` | 老 claim 未必无用，让 agent 自己判断；排序上靠后即可 |
| token 预算 | **由知识库按价值裁剪** | agent 上下文有限，让库自己保留最高价值 claim，比让 agent 截断字符串合理 |
| 价值排序 | 事实×1.3、数据×1.25、观点×0.75、预测×0.6，再乘权威度权重与时效衰减 | 决定预算裁剪时保留谁，不能只看 confidence |
| 观点冲突 | **不做合并**，强制分组为共识/分歧/存疑 | 把冲突平均成「中立结论」会误导决策 |
| 异步任务 | 存内存不落库 | 任务状态是进程内临时信息，落库带来清理/并发/陈旧记录一堆麻烦 |
| 写接口 | 默认关闭，且关闭时 MCP **连工具都不注册** | 不能只靠「调用时拒绝」，减少攻击面 |
| 绑定地址 | 非本机且无 token 时**拒绝启动** | 默默暴露知识库比启动失败危险得多 |
| 只读保证 | annotations 声明之外，**服务端侧也真正只读** | 规范明确要求客户端把 annotations 视为不可信 |
| 订阅调度 | 只支持「每 N 小时」，不做 cron | cron 表达式对单用户工具过度复杂 |
| 订阅去重 | **独立 seen 表**，不靠 sources 判重 | 被密度门槛拒掉的内容不进 sources，否则每次运行都重新抓取评估同一批水文 |
| 订阅反问 | 运行时不反问，按当前解析继续并留痕 | 没人在旁边回答；但要让用户事后能发现指令不够明确 |

### 唯一一次 schema 迁移（v2 → v3）

前五个里程碑都是零迁移，M6 破例：M1 漏了 `subscriptions` 表，
**因为当时把订阅当成「配置」而非「数据」**。实际上它需要记录
`last_run` / 去重游标 / 累计统计，是有状态的数据。

迁移机制本身经受住了考验：自动备份 + 全部 `IF NOT EXISTS`，
重复执行安全（已加测试守护）。

### M6 开发中发现并修复的缺陷

| # | 缺陷 | 影响 | 修复 |
|---|------|------|------|
| 1 | `DataPaths` 当构造器用（实为工厂函数） | 启动即崩 | 改用 `get_data_paths()` |
| 2 | MCP SDK 装饰器 API 不存在 | 按旧版规范写的 `@server.list_tools()` 全部失效 | 新版改用 `MCPServer` + `@tool`，反而更好——schema 从类型注解自动生成 |
| 3 | **claim 检索整串 LIKE** | 「国债 利率」这类多词查询**必然失配**，agent 拿不到任何数据。这个 bug 同时影响已有的 `distill claims` 命令 | 按词切分 OR 匹配 |
| 4 | **claim 检索只有词面匹配** | 查「利率」匹配不到「LPR」，违背 AGENT_API.md「语义+关键词混合」的承诺 | 补一路语义检索合并进结果 |
| 5 | **语义路无相关性门槛** | 查「加密货币挖矿」（库里完全没有）返回一堆无关 claim，coverage 判成 `sufficient`——**这正是 §9 要防的「库里没知识时 agent 硬答」** | 加余弦相似度门槛。实测定标：相关 0.53~0.68、无关 0.32~0.44，取 0.50 并做成可配置 |
| 6 | 用 RRF 融合分做门槛 | 融合分约 1/60 量级且**只表达排序、不含相关性**——三个完全不同的查询分数一模一样，门槛形同虚设 | 改用 `_vector_search` 的余弦相似度本身 |
| 7 | **未建索引时仍加载 embedding 模型** | 白等十几秒后必然失败。测试从 2 秒涨到 **60 秒**；生产上 agent 调用同样不能忍 | 先用 `count_indexed()` 做便宜的前置检查 |

**第 5 和第 7 条最值得记：**

第 5 条说明**语义检索的默认行为对 agent 场景是危险的** —— 它总会返回
「最相似」的结果，哪怕毫不相关。人看到不相关结果会自己忽略，
agent 会当成证据用。这类缺陷只有在真正模拟 agent 调用链时才会暴露。

第 7 条是性能与正确性的交汇：加语义路本身是对的，但没想到它会在
无索引时触发模型加载。**测试耗时 30 倍恶化是个很好的信号** ——
如果只看功能测试通过就收工，这个问题会留到用户第一次调 agent 接口时才发现。

## 2026-09-16 · Windows 打包方案

### 核心判断：不用 PyInstaller

打包成单文件 exe 是「分发给不懂技术的最终用户」的方案，用在这里是过度工程：

| 方案 | 为什么不选 |
|------|-----------|
| PyInstaller / Nuitka | torch + sentence-transformers 打包后 **2GB+**；模型文件仍需运行时下载；**必须在 Windows 上打包**（不能交叉编译）；出错信息难定位；**每次改代码都要重打 2GB**，与「持续迭代」直接冲突 |
| Docker | Windows 上要 WSL2 + Docker Desktop，比装 Python 重得多；CUDA 透传配置麻烦 |
| 离线 wheel 包 | wheel 是平台特定的，**必须在 Windows 上 `pip download`**，在 macOS 上下载的是 macOS wheel——这个坑很隐蔽 |
| **源码 + venv 重建** | 选它 |

理由：这是**自用且会持续迭代**的工具。整个 PORTABILITY.md 的设计
（相对路径、compat 适配层、可选依赖组）本就是为这个方案服务的。
改一行代码立刻生效，而不是等 20 分钟重新打包。

### 打包脚本要解决的实际问题

手动 zip 整个目录会带上几样致命的东西：

| 必须排除 | 后果 |
|----------|------|
| `.venv/` | macOS 二进制 + 写死的绝对路径，拷过去 pip/python 全失效，且报错难懂 |
| `config.yaml` | **含 API Key** |
| `*.egg-info/` | 内含本机绝对路径 |
| `data/audio/` | 几 GB 音频，而转写结果已在库里，重下成本远低于传输 |

`data/distiller.db` 反而要带（含 WAL 旁文件）—— 库内只存相对路径，
零转换可用。这是 M1 那个设计决定第一次真正兑现价值。

### Windows 安装脚本的三个自动处理

1. **Python 版本校验** —— 不满足 3.11~3.14 直接给安装指引，
   而不是让 pip 抛难懂的依赖错误。
2. **误拷 venv 检测** —— 目录里若有非 Windows 的 venv 就删除重建。
3. **PyTorch 版本选择** —— 检测 NVIDIA 显卡。**没独显时装 CPU 版省 2.3GB**；
   CPU 版除转写慢（1 小时音频 15–25 分钟 vs CUDA 3–6 分钟）外功能一致，
   而且有字幕的视频根本不走转写。

### 打包时发现的两个真实缺陷

两个都是「文档承诺了但实现没跟上」，**只有真的走一遍全新安装才会暴露**。

| # | 缺陷 | 影响 |
|---|------|------|
| 1 | **`all` extra 从未定义** | PORTABILITY.md §4 一直写着 `pip install -e ".[all]"`，而 pip 对不存在的 extra **只给 warning 不报错**。用户以为装全了，实际只有核心依赖，然后 `distill serve` 报缺依赖——错误信息完全指不到真正原因 |
| 2 | **OCR 依赖在 Python 3.13+ 无法安装** | `rapidocr-onnxruntime` 所有版本都要求 `<3.13`，而 python.org 现在默认下载 3.13/3.14。照文档装**必然失败** |

第 2 条的根因是 RapidOCR 在 2.x 改了包名，且 API 也变了：

| 包 | Python | 调用与返回 |
|----|--------|-----------|
| `rapidocr-onnxruntime` 1.x | 仅 <3.13 | 吃 `BytesIO`，返回 `(list[[box,text,score]], elapse)` |
| `rapidocr` 3.x | 3.13/3.14 可用 | 直接吃 `bytes`，返回对象，文本在 `.txts` |

选择**双包兼容**而非直接切新包：依赖用环境标记按 Python 版本选，
代码 try-import 并适配两种返回格式。老环境不用动，新机器也能装。

**教训**：跨平台承诺不能只靠「依赖都是纯 Python / 有预编译 wheel」这种
静态判断 —— **依赖自身的 Python 版本支持窗口会随时间关闭**。
`rapidocr-onnxruntime` 当初选的时候没问题，是 Python 往前走了。
定期在目标 Python 版本上跑一次全新安装，是唯一可靠的验证方式。

## 2026-09-18 · 接真实 LLM 实测 10 期：schema 与 prompt 都站得住

配上 DeepSeek key 后跑了 10 期，这是第一次用真实模型验证问答 schema。

### 结果

| 指标 | 预估 | **实测** |
|------|------|---------|
| 单期成本 | $0.00060 | **$0.00036** |

### prompt 里最关键的那条要求确实生效了

要求「纠正 ASR 音译错误」不是可选项，是决定可用性的：

| 字幕原文 | 模型输出 |
|---------|---------|
| 库达 | CUDA |
| 西塔 | θ / theta |
| moo e | MoE |
| soft max | softmax |
| 拆分（指 TD 误差） | δ |

数学表达也按要求规范化了。GAE 那期从**完全无标点的字幕**还原出

MLA 那期还原出 `O = (A·C_KV)·(W_UV·W_O)` 的结合律重排——
这些在抽取式下**结构上不可能**得到。

### 一个意外收获：标题也被纠正了

模型读完正文后补全了标题里被省略的信息。这是设计时没想到的价值。

- `PRAGMA foreign_key_check` 通过，无悬空引用
- claims / relations / entity_mentions 全部完整

- 重跑同一条无法复现

## 2026-09-18 · 问答体独立 schema：抽取式的天花板

**反馈**：「抓这个系列抓得还行，但是实际内容没法看。我期望的 qa 集合其实是
每期视频里的主问题是什么，引申问题是什么，然后对应的答案是什么，
答案是简略版本的。我方便快速把这些东西都学会」

**这个反馈是对的，而且指出了一个我之前没说透的根本问题。**

### 抽取式的天花板在哪

之前导出的 211 题，「要点」是从无标点的 AI 字幕里按连接词切句、
再按关键词打分挑 4 句。这套办法**结构上做不到**用户要的东西：

| 用户要的 | 抽取式能否做到 | 原因 |
|---------|--------------|------|
| 主问题 | ✅ 能 | 标题即问题，解析即可 |
| **一句话简答** | ❌ **不能** | 归纳概括是生成任务，摘录做不到 |
| 引申问题 | ❌ 不能 | 需要理解内容才能判断什么算「延伸」 |
| 术语正确 | ❌ 不能 | 「库达」=CUDA、「西塔」=θ、「moo e」=MoE 需要理解上下文才能纠正 |

我之前只标注了「这是原文节选而非模型摘要」，但没说清**节选永远
到不了用户要的形态**。诚实地讲，那份文档的可用性确实不够。

### 决定：问答体走独立 schema

参照论文已有的做法（论文走 问题/方法/实验/局限 独立 schema），
新增第三种产物 `QAContent`：

```
main_question    主问题（纠正术语后的规范表述）
answer_brief     一句话直答，≤60 字   ← 这是「简略版本」的核心
answer_points    推导/步骤，3~5 条
prerequisites    前置概念
follow_ups       引申问题 + 各自简答
pitfalls         易错点
```

字段顺序即阅读顺序：**扫 brief 判断懂没懂 → 不懂看 points →
想深入看 follow_ups**。这是「快速学会」的路径，不是「完整记录」的路径。

四个实现决定：

**① 挂在 `Digest.qa` 而非新建表。**
`digests.payload_json` 存的是整个 Digest 的 JSON dump——加字段零迁移。
这是当初存 JSON 而非拆列的设计在第七次改动上继续兑现。

**② 不走 map-reduce，单次调用。**
问答体单期约 850 字（实测 211 期平均值），一次调用装得下。
分块会把推导过程切断，反而降低答案质量，还把成本翻几倍。

**③ 独立任务名 `qa_card`，默认用 chat 而非 reasoner。**
原本想复用 `reduce`，但配置里 `reduce` 配的是 `deepseek-reasoner`。
211 期批量跑时 chat 与 reasoner 的成本差好几倍，而这种
「把一段话整理成结构化答案」的任务 chat 完全够用。

**④ prompt 里显式要求纠正 ASR 音译错误。**
这是关键——不说的话 LLM 会原样输出「库达」「西塔」「soft max」。
把常见错误列进 prompt（"库达"=CUDA、"西塔"=theta、"moo e"=MoE），
并要求数学表达用规范写法（√dk 而非「根号dk」）。

### 判定要保守

`is_qa_title()` 要求明确的疑问信号（问号，或如何/为什么/是什么等疑问词）。
**误判成问答体的代价大于漏判**——通用内容被误判会拿不到
大纲/概念/金句，而问答体被漏判只是退化成普通摘要。

### 配套：`distill-pending`

正文已在库里（211 期、18.3 万字），不该为了补浓缩重新采集一遍——
平台限流、字幕接口可能失效、无字幕的还要重跑转写。

新增 `Pipeline.redistill(source_id)`：从库内 segments 重建 RawContent
再走 `process`。注意必须传 `force=True`，否则库里已有 source 记录
会被当成「已消化」直接复用。

```bash
distill distill-pending --series "每天一个宝藏问题"
```

### 实测成本（真实数据算的）

211 期 · 平均 857 字/期 · prompt 开销 1227 字：

| 项 | 值 |
|----|-----|
| 单期 token | 入 3127 / 出 570 |
| DeepSeek 价 | 入 $0.14/1M · 出 $0.28/1M |
| **全系列** | **$0.126（约 0.91 元）** |
| 占月度预算 | 1.3% |

### 未完成

**本机仍无可用 LLM**（无 API Key、Ollama 未安装且 macOS 只有 GUI 安装包，
我不代装应用）。链路已用假 LLM 端到端验证通过——
schema 解析、tldr 回填、渲染、成本记录都正确。

**465 项测试通过**（新增 30 项）：
`is_qa_title` 的正反例、单次调用而非 map-reduce、
用 qa_card 任务名、tldr 一起填、LLM 返回空不崩、
无 question 的 follow_up 被丢弃、brief 渲染在最前且加粗、
空字段不留空标题、redistill 不重新采集且传 force。

## 2026-09-18 · 批量导入可用性：修自己踩过的坑

**提问**：「你按你的想法把性价比比较高的优化点弄一下吧」

**选择依据**：不从需求池挑推测性需求，而是修**这三轮实测中自己真实踩到的**问题。
判断标准很直接——抓 211 期时我最后是绕过 CLI、自己写脚本配 `nohup` + `tail`
才跑完的。**核心场景需要绕过工具才能完成，这本身就是缺陷**。

### ① `--subtitle-only`

`--no-distill` 只关「浓缩」不关「转写」。批量跑到无字幕视频会静默启动
本地 Whisper：CPU 482%、内存 4.3GB、单条数分钟，日志毫无提示。
我第一次直接误判成死循环 kill 了进程，用 `lsof` 看到 PyAV 才明白。

两个配套决定：
- 新增 `SubtitleMissing`（继承 `FetchError` 保持既有错误处理兼容），
  让「按预期跳过」与「真失败」**分开统计**。
  混在一起报「失败 30 条」会让人以为出了问题，进而去排查根本不存在的故障。
- 不加该参数时，转写前打印时长预估与 `--subtitle-only` 提示。
  **静默的慢比报错更难排查**，这是这次最大的教训。
- `add` 里 `SubtitleMissing` 用**退出码 0**：它不是错误，
  脚本里循环调用时不该被当成失败中断。

### ② 批量过程可观测

| 改进 | 原来的问题 |
|------|-----------|
| `[i/N]` + 剩余时间估算 | 完全不知道还要多久 |
| 进度与标题分两行 | 拼一行会折行，反而看不清进度 |
| 失败清单（URL + 原因） | 只报「失败 N 条」，不知是哪些 |
| Ctrl-C 优雅中断 | 原来抛 traceback，不知已完成多少、能不能续 |
| 总耗时 | 无法估算下次同类任务 |
| `find` 支持 `--no-distill` | 无 LLM 时批量入库只能用 `add` 逐条 |

两个细节：
- **前 3 条不估算 ETA**——样本太少，给出的数字会误导。
- 续跑靠幂等而非断点文件：已完成的都已入库，重跑自动跳过。
  不引入状态文件是有意的，少一个会失同步的东西。

### ③ 顺带修掉一处静默截断

`qa-export --limit` 默认 200。我自己导出 211 题时如果忘了加 `--limit 300`，
会**静默少 11 题**且输出显示「✓ 已导出 200 题」。

这类「看起来成功了」的截断最危险——没有任何信号提示你数据不全。
改为默认不限量（`limit=None`）。

**这三条的共性**：都不是功能缺失，而是**工具在悄悄做与用户预期不符的事**。
静默降级、静默截断、静默慢，比直接报错难查一个数量级。

### 交付
**435 项测试通过**（新增 14 项）：
subtitle_only 的四种分岔（无字幕拦、有字幕过、文章不受影响、异常继承关系）、
时长格式化（含负数与零的边界）、导出范围解析（默认不限量、显式限量、
ID 区间不被截断）。

**提问**：「我想要这个系列全部的，然后都整理出来，还有就是项目目录你整理下，

先查了引用关系：**10 个根目录文档之间有 59+ 处交叉引用**，

所以决定：项目文档原地不动，只隔离 case 产物。

```
cases/                          # 新增，已 gitignore
```

隔离理由写进了 `cases/README.md`，三条都是实际考虑：

### 两处硬上限会静默截断

`_discover_uploader` 里 `pool_size` 封顶 300、翻页写死 `page <= 10`

**会在第 300 条截断且没有任何提示**——用户要全系列，拿到的是一部分。

这在语义上讲得通（转写属于采集），但对「我只要字幕」的批量场景是陷阱：
**一条无字幕视频能把 200 条的批量任务拖住十几分钟**，而且看不出在干什么。

## 2026-09-18 · 实测「海安雨 · 每天一个宝藏问题」系列 → Q&A 合集

**提问**：「让工具总结 bilibili 一个 up 主海安雨的一个系列，系列名里有每天一个宝藏问题，
专门讲 llm 的……输出形式我希望是一个 q&a collection 的文档」

这次暴露的是**两个能力缺口**（不是 bug）加**三个静默失效**。

### 缺口 1 · 工具没有「系列」概念

此前只能按 UP 主 + 主题（语义打分）或全站关键词检索，
但用户说的「每天一个宝藏问题系列」是**标题必含词**，不是语义方向。
这两者结果差别很大：语义打分会把同 UP 主其他讲 LLM 的视频也算进来。

新增 `extract_series()`，识别三种自然写法：
`【每天一个宝藏问题】` / `XX系列` / `XX合集`，
结果写进已有的 `filters.include_keywords`（ranker 本就支持，白白没人用）。

一个坑：「海安雨的每天一个宝藏问题系列」要在「的」处切断，
否则 UP 主名被吞进系列名，标题过滤一条都匹配不上。

实测另一个发现：**B 站空间搜索的 `keyword` 是模糊匹配**，
传「每天一个宝藏问题」只把 399 条投稿缩到 386 条，几乎不起作用。
真正生效的是本地标题过滤，因此有系列过滤时必须**扩池到 4 倍**——
否则用户要 12 条、系列占比一半时只能拿回 6 条。

### 缺口 2 · 没有 Q&A collection 输出

已有 vault（Obsidian 双链）、brief（简报）、markdown（单篇），
但问答体系列内容用这些格式都不合适——
标题即问题、正文即答案，天然该按「问题 → 要点 → 出处」组织。

新增 `review/qa.py` + `distill qa-export`。
与 vault 的区别：vault 按「内容」组织成多文件强调关联，
qa 按「问题」组织成单文档强调可检索、可通读。

**关键设计：无 LLM 时不空手而归。**
浓缩结果缺失时退化为抽取式节选，并在文档顶部用 ⚠ 显眼声明
「这是原文节选而非模型摘要」。不声明的话用户会把节选当成结论。

### 静默失效 1 · cookie 配了但包没装

`config.yaml` 写着 `cookies_from_browser: chrome`，
`browser_cookie3` 却没装，`except Exception` 把 ImportError 吞了，
B 站投稿列表直接返回 `code=-352` 风控错误。

**用户以为自己配好了登录态**——这比没配更难排查。

修：加进主依赖；`doctor` 增加「浏览器Cookie」一行，
且**实际读一次 cookie** 而非只检查包是否安装——
浏览器没登录、profile 变了、macOS 钥匙串拒绝授权，
都会让 cookie 为空而没有任何提示。现在会明确区分这几种情况。

### 静默失效 2 · AI 字幕完全没有标点

实测 B 站 AI 自动字幕是这样的：

> 今天的问题是如何可视化moo e先要问如何可视化transformer之前提供了一种超简单可视化方案就是Q按行分K的转置按列分…

**连续 130 字零标点。** 抽取式摘要按句号/逗号切句会一条都得不到，
第一版导出的文档里每个要点都是 130 字的巨型残句。

改为双策略：有标点按标点切；无标点按口语连接词切
（「然后」「所以」「那么」「因为」…）——这些词在中文口语里
几乎总出现在语义边界上。

### 静默失效 3 · 长度下限误杀结论句

抽取式打分曾设 `len(s) >= 16` 挡碎片，结果把
「所以优势的本质是比平均好多少」（14 字）这类**最有价值的结论句**滤掉，
反而留下长而空的句子，以及「好了本期就到这里关注我点赞三连」。

教训：**语义完整性不该用长度一刀切**。
改为下限放回 10，靠「悬垂结尾惩罚」（以「的/了/是/而」等收尾说明被切断）
和「引流话术重罚」来判断。引流惩罚要给 -100 而非 -3——
长句的长度分 +1.0 加术语分 +0.7 能把 -3 抵消掉。

- 导出 `海安雨-每天一个宝藏问题-QA合集.md`，154 行，
  含目录、12 题、每题带原片链接与库内编号。
- **415 项测试通过**（新增 18 项：标题解析、无标点切句、
  引流过滤、原文顺序、节选声明等）。

**唯一未完成**：要点仍是原文节选而非模型摘要——本机无可用 LLM。

## 2026-09-17 · 实测「B站 ai infra 排名第一的视频讲了什么」：修 5 个 bug

**提问**：「现在我想看 ai infra 搜索排名第一的视频主要讲了什么，你能做到吗」

能力本身早就有（`distill find` + `TargetType.KEYWORD`），但**真跑一遍才发现
从解析到转码有 5 处坏的**。这类 bug 的共同特征是：**不报错，只给错结果**。

### Bug 1 · 英文词组被空格截断（最严重）

`_guess_name` 的字符类 `[\u4e00-\u9fffA-Za-z0-9]` 不含空格，且 lookahead 含 `\s`，
于是「ai infra」被截成「ai」。

搜 `ai` 和搜 `ai infra` 是**完全不同的结果**，而且不会报错、不会有任何提示。
英文技术词组内部有空格是常态（vector database、rust async、llm inference），
这个 bug 会静默影响所有英文关键词检索。

修：英文分支显式允许空格连接 `[A-Za-z0-9]+(?:[ \-_][A-Za-z0-9]+){0,4}`，
遇中文或修饰词才停止；`_strip_modifiers` 末尾也把连续英文 token 合并
（否则 `parts[0]` 同样会截断）。

### Bug 2 · 「排名第一」完全没被识别

`extract_limit` 只认「前N」「N条」「topN」，不认「第N」。
结果用户只想看 1 个视频，工具默认抓 20 条——**20 倍的时间与花费**。

### Bug 3 · 关键词搜索默认按播放量排序

这个最微妙。用户说「搜索排名第一」，指的是 B 站搜索框里的第一条（综合排序
`totalrank`），而工具默认 `RankBy.PLAY` 会给出**另一个视频**——
通常是某个爆款泛科普，而非搜索引擎认为最相关的那条。

差异用户看不见，只会觉得「工具给的不是我要的」。

修：`_RANK_HINTS` 增加 `RELEVANCE`（"排名"/"综合排序"/"相关度"）；
且 KEYWORD 目标无显式排序词时默认 `RELEVANCE` 而非 `PLAY`
（UPLOADER 场景保持 PLAY——找某人最受欢迎的作品是合理默认）。

顺带修掉 `_discover_keyword` 里误用 `_SPACE_ORDER`（UP 主空间的排序表）
判断关键词搜索是否原生支持该排序，导致 relevance 被当成「不支持」
而抓 3 倍候选，limit=20 时白跑 2 页请求。

### Bug 4 · doctor 假阳性：报 ffmpeg ✓ 但转写必然失败

`doctor` 显示 `ffmpeg: ✓`，实跑却报
`ffprobe and ffmpeg not found`。

根因：`find_ffmpeg()` 兜底到 imageio-ffmpeg 自带的二进制，它确实存在且可执行，
所以 `has_ffmpeg=True` 没说错。但——
1. 那个文件叫 `ffmpeg-macos-aarch64-v7.1`，而 yt-dlp 在 `ffmpeg_location`
   目录下**按标准名** `ffmpeg`/`ffprobe` 查找，找不到；
2. imageio-ffmpeg **完全不提供 ffprobe**，而 yt-dlp 的音频后处理需要它。

**doctor 全绿但功能必然失败，比 doctor 直接报红危险得多。**

修法没有去迁就 yt-dlp 的查找规则（软链、改名都很脆弱），而是
**把转码收回自己做**：yt-dlp 只下载原始音频流，转 16k 单声道 wav 由我们用
已解析的确切路径调用 ffmpeg 完成。这样既不依赖二进制文件名，也不需要 ffprobe。
转码失败时保留原始文件——faster-whisper 内部用 PyAV 解码，多数容器能直接读，
不该因为转码失败就放弃整条链路。

### Bug 5 · B 站搜索限流与「确实没有」无法区分

连续搜了几次后，接口返回 `code=0` + 空 `result`，
代码 `if not results: break` 静默返回 0 条，界面显示
「没有符合条件的内容。可放宽主题或时间范围。」

用户会以为**真的没有这个内容**，而实际等 1-2 分钟就能拿到。
（这个 bug 是在本次实测中真实触发的——同一个查询前一次返回 19 条，
后一次返回 0 条。）

修：第一页就空且无任何候选时，明确报错并给出 4 条排查路径。
同时给 `config.example.yaml` 的 bilibili 加 `rate_limit_sec: 2.0` 默认值——
搜索接口比普通页面敏感得多。

### Bug 6 · 提示指向不存在的选项

成本预演打印「1 条已在库中，将跳过（--force 可重跑）」，
但 `find` 命令**没有** `--force`（只有 `add` 有）。

修：给 `find` 补上 `--force`，并让它把已在库的重新纳入待处理。

### 实测结论

链路跑通：搜索 → 选材（19 条候选取 totalrank 第一）→ 采集 →
字幕/转写（**2546 字 / 13 段入库**）。

唯一未完成的是最后一步浓缩——本机无任何可用 LLM
（deepseek 无 API Key、ollama 未启动），与代码无关。

386 项测试全程无回归。

## 2026-09-17 · 平台采集器配置化

**提问**：「能导入的社交平台做成可配置的，这个设计现实吗？比如小红书，知乎，bilibili，抖音」

**关键判断：这个问题要拆成两层，答案完全相反。**

### 第一层：开关 + 参数 —— 现实，做了

平台之间风控强度差异很大，全局一套参数不够用：
小红书连续请求极易触发验证（必须限流），B 站不配 cookie 拿不到字幕，
普通网页什么都不需要。此前这些只能全局配。

新增 `PlatformConfig`（每平台 enabled / cookie / proxy / UA / timeout /
retry / rate_limit / headers），`IngestConfig.effective(name)` 把平台级
覆盖合并进全局，采集器只看这一份，不必自己判断「有没有覆盖」。

**一个设计决定值得记**：禁用某平台后，该平台链接**明确报错而非降级到通用抽取**。

实现过程中这里真的出了 bug——通用兜底器对所有 URL 都 `match`，
第一版写成「跳过禁用的继续找下一个」，结果禁用小红书后
悄悄降级到了 `web`。而小红书正文在嵌套 JSON 里，通用抽取只能拿到空内容。
**给用户残缺数据却不说原因，比直接报错危险得多。**
改为以 `FALLBACK_PRIORITY` 为界：专用采集器被禁用则直接失败。

### 第二层：用 YAML 声明新平台 —— 对这四个平台不现实

先看现有采集器实际在做什么，这是判断依据：

| 采集器 | 行数 | 平台特有逻辑 | 能用选择器表达 |
|--------|------|-------------|--------------|
| bilibili | 252 | **WBI 签名**（64 位混淆表 + 动态 key + md5）、字幕优先级排序、碎句合并 | **否，是算法** |
| xhs | 135 | `__INITIAL_STATE__` + 嵌套 JSON **广度搜索**定位 note（路径会变，不敢硬编码） | **否** |
| zhihu | 115 | 私有 API `/api/v4/...`、URL 模式区分文章/回答 | 部分 |
| wechat | 109 | `data-src` 懒加载、OCR 触发判断 | 部分 |

**一句话：声明式解决「解析」，解决不了「拿到」。**
拿不到内容的平台，配一百个选择器也没用。

### 但第二层有个有价值的子集 —— 也做了

对「正文在固定 DOM 节点」的站点（个人博客、新闻、文档站），
声明式配置完全可行。这类站点在「通用网页」里占大多数，
而 trafilatura 对结构特殊的页面（带侧栏的文档站、长评论区）经常抽进噪声。

`SiteRule` + `DeclarativeAdapter`，三个实现细节：
- **优先级 50**（内置专用 10，通用兜底 100）——用户显式写的规则该优先于
  通用抽取，但不能盖掉专用采集器（为 bilibili 写选择器是没意义的）。
- **逐个块级子节点取文本**而非直接 `text_content()`，否则所有段落被挤成一行，
  丢掉段落边界会影响后续分块。
- **同时支持 CSS 与 XPath**（以 `/` 判定）。CSS 覆盖 95% 场景且大家都熟，
  但按文本定位、取属性这类只有 XPath 能表达。
- 选择器失效（站点改版）时明确报错并指出是哪个选择器，不静默抽空。

代价：新增 `cssselect`（30KB 纯 Python，跨平台零风险）。`lxml` 本就随 trafilatura 进来了。

### 抖音：不建议做，但原因不是技术

技术上确实最难（`X-Bogus`/`a_bogus` 签名 + 设备指纹 + 无公开字幕接口，
签名算法混淆在 JS 里且频繁变动）。**但真正的问题在产品层面**：

这个工具的定位是「把低信息密度内容压缩成高密度结论」。
抖音主体是 15~60 秒短视频——30 秒转写出来约 100~150 字，
浓缩后还不如原标题信息量大。**压缩没有意义，因为它本来就没有可压缩的冗余。**

B 站一个 40 分钟视频压成 5 条结论是真实价值；
抖音 30 秒视频压成 1 条结论，等于什么都没做。

**替代路径现在就能用，不需要开发**：`yt-dlp` 已是依赖且支持抖音，
下载后 `distill add 文件路径` 走本地转写（#1 已实现），绕过签名问题。
如果主要看抖音上的长视频（知识类 10 分钟以上），这条路完全够用。

- **386 项测试通过**（新增 18 项）。
- 新增 `tests/test_ingest.py`：默认全启用、禁用不降级（回归）、
  单平台禁用不影响其他、平台覆盖全局、采集器看到合并后配置、
  声明式抽取字段/保段落边界/删噪声/标题兜底/选择器失效报错/

- 新增 `distill platforms` 与 `--test <url>`，实测各平台状态与路由正确。

## 2026-09-17 · 实际使用测试：「总结影视飓风最近 3 个视频」

拿一句最自然的日常指令去跑，抓到 **6 个缺陷**，其中一个是严重的静默失效。

### 缺陷 1（严重）：中文 BM25 完全失效

正文里明明有「山西」，`FTS MATCH "山西"` 返回 **0 条**。
即混合检索的关键词一路对中文**完全无效**——而这个工具主要处理中文，
等于一直在用纯向量检索，却以为混合检索在工作。

**根因**：SQLite 的 `unicode61` 分词器把连续中文当作**一个 token**。
「这一次我们去了一趟山西」整串是一个 token，查「山西」自然匹配不到。
查询侧早已做了二元组切分，但**索引侧没做**，两边对不上。

**为什么没被早发现**：这是典型的静默失效——不报错、不崩溃，
只是少了一路召回。语义检索仍能返回结果，看上去一切正常。
M2 的测试只测了查询侧分词函数，没做「索引→查询」的端到端验证。

| 方案 | 结论 |
|------|------|
| `trigram` 分词器 | 否决。要求查询 ≥3 字符，而「山西」「折叠」「降息」这类 2 字词是中文检索最常见形态（实测返回 0） |
| **索引侧也存二元组** | 采用。「去了一趟山西」→「去了 了一 一趟 趟山 山西」 |

代价是 FTS 索引体积约 2 倍，个人库规模完全可接受——
换来的是关键词召回从「完全失效」变成「可用」。

**实施**：外部内容表模式下触发器只能塞原文（SQL 里做不了字符串切分），
因此改为独立 FTS 表 + Python 侧写入（v4 迁移）。
切分逻辑抽到 `store/fts.py`，**索引与查询共用同一函数**——
两边各写一份正是缺陷的根源。

修复后同一批数据：「山西」「折叠屏」「阿信」「煤炭」全部精确命中，
混合检索的 Top1 从「语义#1」变成「语义#1+关键词#1」。

### 缺陷 2–4：自然语言指令解析

「影视飓风最近3个视频」一句话里三处都错：

| 项 | 错误结果 | 后果 |
|----|---------|------|
| 关键词 | `影视飓风最近` | 粘上时间词，搜不到任何结果 |
| 排序 | `play 降序` | 用户要最新 3 个，却给播放量最高的 3 个——**完全是另一批视频，且无任何提示** |
| 类型 | `keyword` | 全站搜关键词，而非取该 UP 主投稿 |

根因分别是：「最近」不在排序词表里（只有「最新」）；
名称清洗正则没覆盖「最近」；`「X的视频」` 分支**直接 return 跳过了全部清洗逻辑**。

难点在于「最近」有两种语义，不能一刀切：
- 「最近半年 播放量前5」→ 时间范围修饰，排序仍按播放量
- 「最近 3 个视频」→ 时间倒序

判据是看「最近」后面跟的是**时间单位**（天/周/月/年）还是**数量单位**（个/条/篇）。

### 缺陷 5：ASR 可用性展示误导

`doctor` 显示 `ASR: faster-whisper` 像是可用，
实际缺 `yt-dlp` 根本下载不了音频。转写是一条链
（ASR 引擎 + 下载器 + ffmpeg），缺一环都跑不通，
只报其中一环会让人误判。改为先给结论再列明细。

### 缺陷 6：成本预演把「未探测」说成「无字幕」

发现阶段不探测字幕（避免为每条候选多发请求），
但展示成「有字幕 0 条」，让人以为确实都要转写。
实测差距 10 倍（有字幕 16s vs 未探测上限 166s），
这个措辞会让用户高估成本而放弃。改为明确标注「字幕情况待确认 —— 以下为上限估算」。

### 顺带修的两处

- `subscribe` 的 B 站音频下载遇到 412/403 只抛原始错误，
  改为识别为风控并给出 cookie 配置指引。
- 两处测试把 schema 版本号写死成 `"3"`，每加一次迁移就会误报。
  改为断言 `SCHEMA_VERSION` 常量。

### 教训

**只跑单元测试和构造的样例，发现不了这类问题。**
中文 BM25 失效藏了整整四个里程碑，因为：
① 它不报错；② 语义检索掩盖了症状；③ 测试只覆盖了函数而非链路。

真正抓到它的是「拿一句真实的话，用真实的数据，跑完整条链路」——
这个成本远低于它可能造成的长期误判。

### 交付验证
- **362 项测试全通过，3.8 秒**（新增 12 项）。
- 新增 `TestChineseBm25` 做端到端验证：索引→查询全链路，
  覆盖 2 字词命中、不误召、英文大小写、重建恢复、
  重新入库清理陈旧 FTS。
- v3 旧库升级实测：自动备份 `old.backup-v3.db` → `doctor` 提示需重建
  → `distill index --rebuild-fts` 秒级恢复 → 命中恢复正常。

## 2026-09-16 · M5 完成：网页版

### 核心判断：不引入 Node 前端工具链

你明确要求「适合迭代 + 易迁移到 Windows」，所以**不上 React/Vue**：

| 方案 | 代价 |
|------|------|
| React/Vue SPA | 需 Node + npm + 构建配置；Windows 上多一整套依赖生态；改代码要等构建 |
| **Jinja2 + 原生 JS** | 纯 Python 依赖（fastapi/uvicorn/jinja2 三个包）；`pip install` 即可跑；改完刷新见效 |

单用户本地工具的交互复杂度撑不起 SPA 的代价。同理**不引入 d3**画图谱——
力导向只需斥力/弹簧/向心力三条规则，手写百来行，省 250KB 依赖。

### 深链：网页版相对 CLI 的核心增量

CLI 里看到 `02:05` 只能自己拖进度条，网页里点一下就跳到视频那一秒。

**关键取舍：不猜平台参数名。** 各平台格式不同（B 站 `?t=125`、
YouTube watch 页 `?t=125s`、embed 页 `?start=125`），猜错会**静默跳到
视频开头而不报错**——属于最危险的失败模式。因此只登记已确认格式的平台，
其余原样返回原文链接（保证永远可点）。

其他细节：
- 分 P 视频的 `p=` 参数必须保留，否则跳回第一 P
- 有 `start_ms` 时直传秒，不走「格式化成字符串再解析回来」
- 章节名/段号锚点（`#12`、`introduction`）渲染成纯文本而非链接

### 架构取舍

| 问题 | 决定 | 理由 |
|------|------|------|
| 数据库连接 | **每请求新建** | SQLite 连接不是线程安全的，而 uvicorn 用线程池跑同步处理函数，共享连接会偶发 `ProgrammingError` |
| 页面 vs API | 页面只读，写操作全走 JSON API | 职责清晰；且 API 挂了 OpenAPI，**M6 的 agent HTTP 接口可直接复用这一层** |
| 首屏渲染 | 阅读页服务端渲染，列表页前端拉取 | 阅读是核心场景，内容不该等 JS 请求完才出现 |
| 原文片段 | 按需加载 | 长视频转写可能上万字，不该塞进首屏 |
| 回答渲染 | 手写 markdown 子集 | 回答格式受 prompt 约束，只需段落/列表/加粗/行内代码，几十行够用，省一个依赖 |
| 监听地址 | 默认 `127.0.0.1` | 本服务无鉴权；用 `--host 0.0.0.0` 时明确警告 |
| 可执行项勾选 | 写成 `done` 批注 | 与 CLI 的 `distill note -t done` 同口径，简报便不再提醒 |

### M5 开发中发现并修复的缺陷

| # | 缺陷 | 影响 | 修复 |
|---|------|------|------|
| 1 | `DataPaths(...)` 当构造器用 | **启动即崩**。它是 dataclass 只收 root，实际应调工厂函数 `get_data_paths()` | 改用工厂函数 |
| 2 | **金句锚点永远为 null** | 大纲能跳转、金句不能——而金句恰恰是最想跳回去听原声的部分。根因有两层：① `Quote()` 构造时丢弃了 `chunk_idx`；② **prompt 里从没要求模型返回 `chunk_idx`**，所以就算代码接了也拿不到值 | 补 `Quote`/`Concept` 的 anchor 解析，并在 reduce prompt 里显式要求 `chunk_idx` 且说明它决定能否跳回原视频 |
| 3 | 库内文本直接进 `innerHTML` | 标题来自外部网站，含 `<script>` 会被 XSS | 所有插入点过 `esc()`；加测试守护 |

**关于第 1 条**：这与 M4 的「凭记忆写 SQL 列名」是同一类错误——
对已有 API 的印象不等于实际签名。教训是**跨模块调用前先确认签名**。

**关于第 2 条**：这是个只在端到端验证时才会暴露的缺陷。单看代码
「anchor 字段存在且有赋值逻辑」不会觉得有问题，只有真的点开页面
发现金句旁边没有可点的时间戳才会察觉。**说明端到端验证不能省。**
