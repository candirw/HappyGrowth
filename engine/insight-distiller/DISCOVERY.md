# Discovery 层设计 · 自然语言选材

> 目标：输入不再局限于 URL，而是「**说人话**」——
> "影视飓风摄影方向最近半年播放量前 20"、"某专栏收藏量前 100"、"关注的几个 UP 主本周聊 AI 的视频"
> 工具自行解析 → 发现候选 → 筛选排序 → **预演成本** → 确认后批量消化。

---

## 1. 为什么需要单独一层

原方案是 `URL → 消化`。自然语言选材多出三个本质问题：

1. **实体消歧**：「影视飓风」要映射到唯一 UP 主 ID；搜"老师"可能命中 20 个账号。
2. **平台能力不匹配**：用户想按「收藏量」排序，但**B 站空间搜索只支持按播放量/日期排序，没有收藏量排序**；这类落差必须由工具补偿，而不是报错。
3. **成本会失控**：一句话可能炸出 300 个视频，其中 200 个没字幕要走 ASR ≈ 十几个小时算力。**必须先预演再执行。**

所以 Discovery 是独立一层，产出「候选清单」，与后续消化解耦：

```
自然语言指令
   ▼
1. Parse    → Query IR（结构化查询意图）
   ▼
2. Clarify  → 有阻断性歧义才反问；否则用默认值并声明假设
   ▼
3. Discover → 调平台列表/搜索接口，拉候选集（含元数据）
   ▼
4. Filter   → 主题/时间/时长/关键词过滤（两阶段漏斗，见 §5）
   ▼
5. Rank     → 排序取 TopN（平台不支持则本地补齐指标再排）
   ▼
6. DryRun   → 报候选数 / 需 ASR 数 / 预估耗时与花费 → 等确认
   ▼
7. Execute  → 交给原有 pipeline 批量消化，可中断续跑
   ▼
8. Report   → 按信息密度重排，告诉你这批里哪几个真值得看
```

第 8 步是闭环关键：**自然语言帮你「粗选」，密度评分帮你「精选」**。

## 2. Query IR：解析目标

LLM 只负责把人话翻译成这个结构（约束输出 JSON schema，不让它自由发挥）：

```jsonc
{
  "intent": "discover",              // discover 批量发现 | single 单条 | subscribe 转为订阅
  "sources": [
    { "platform": "bilibili",        // bilibili | wechat | zhihu | xhs | web
      "type": "uploader",            // uploader 博主 | column 专栏 | keyword 关键词
      "raw": "影视飓风",              // 用户原话
      "resolved_id": null,           // 消歧后填入
      "confidence": 0.0 }
  ],
  "filters": {
    "topic": ["摄影"],               // 语义方向，最难的一项，见 §5
    "date_range": { "from": "2026-03-16", "to": null },
    "duration": { "min_sec": 300, "max_sec": null },   // 过滤掉短视频/切片
    "include_keywords": [], "exclude_keywords": ["直播回放", "带货"]
  },
  "rank": { "by": "favorites", "order": "desc" },      // play|favorites|likes|date|comments
  "limit": 20,
  "assumptions": ["未指定时间范围，默认最近 6 个月"],   // 自行决定的部分，必须告知
  "blocking_questions": []                             // 必须问清才能执行的
}
```

设计要点：把「工具自行判断」显式化为 `assumptions` 字段——**凡是自己替用户做的决定，都要写出来给他看**，而不是悄悄默认。

## 3. 反问机制：只在错误代价高时才问

反问做过头非常烦人。判定规则：**能推断就推断并声明，只有"猜错会浪费大量时间/金钱"时才阻断提问。**

| 情形 | 处理 | 例子 |
|------|------|------|
| **实体不唯一** | 阻断 · 反问 | "李哥"命中 6 个 UP 主 → 列出粉丝数/简介让你选 |
| **语义真歧义** | 阻断 · 反问 | "专栏收藏量前 100"：指①该专栏文章**被收藏数** Top100，还是②**我的收藏夹**里的前 100 篇？——两者结果完全不同 |
| **量级 / 预算超限** | 阻断 · 确认 | 命中 280 条、其中 190 条需 ASR ≈ 9 小时 → 先问要不要缩到 Top30 |
| **平台不支持该排序** | 不问 · 告知 + 替代方案 | "B 站不支持按收藏量检索，已改为拉播放量 Top300 再本地补收藏数排序，多耗约 40 秒" |
| **主题方向无法从元数据判定** | 不问 · 降级 + 报告置信度 | "标签里没有'美食'，已用标题+简介语义判定，置信度 0.72，可 `--strict` 提高门槛" |
| **时间/时长/数量缺失** | 不问 · 默认 + 声明 | 默认近 6 个月、Top20、时长 > 5 分钟 |
| **明显不合理** | 阻断 · 纠正 | "某 UP 主美食方向"但该号从不发美食 → 直接告知"该账号近 200 条投稿无美食内容，是否搜全站？" |

反问一律用**结构化选项**（可直接数字选择），不做开放式来回聊天，避免多轮消耗。

`--yes` 参数可跳过所有非阻断确认，用于脚本化和定时任务。

## 4. 各平台的发现能力（真实约束）

这是本层最大的工程现实：**每个平台能查什么、能按什么排序，差异极大。**

| 平台 | 可发现范围 | 支持的原生排序 | 关键坑 |
|------|-----------|--------------|--------|
| **B 站** | UP 主全部投稿、全站关键词搜索、分区、收藏夹 | 播放量、日期、弹幕数、评论数 | ①**无收藏量排序** → 需本地补齐；②接口要 **WBI 签名**且变动频繁；③投稿列表**不返回收藏数**，得逐条查详情 → 有请求量代价 |
| **知乎** | 专栏文章列表、用户回答、我的收藏夹 | 时间、赞同数 | 列表接口直接返回 `voteup_count` / `favorite_count`，**排序最容易做**；但需 cookie |
| **公众号** | 单篇 URL、`sogou` 搜索（不稳）、RSS 中转 | 几乎无 | **没有公开的"某号全部文章"接口**，历史文章需靠已有 RSS 服务或手动导出，这是硬限制 |
| **小红书** | 关键词搜索、博主主页、我的收藏 | 有限 | 风控最强，需登录态 + 签名，自动化易封 → **P2，优先支持"导出收藏夹再批量消化"** |

**「收藏量前 100」的落地策略**（以 B 站为例）：
播放量与收藏量强相关，所以不必全量扫描。
`按播放量拉候选 Top 300 → 并发补齐每条的收藏数（带限流与缓存）→ 本地按收藏量重排取 100`。
并向用户明示："这是近似 Top100，基于播放量 Top300 候选池"——**不假装精确**。

配套必需：请求限流（令牌桶）、元数据本地缓存（同一 UP 主重复查询不重复打接口）、失败重试与断点续跑。

## 5. 主题方向判定：两阶段漏斗

「美食方向」「摄影方向」是最难的一环——平台元数据里通常没有这个维度。
**绝不能对 500 条候选逐个跑 LLM**（慢且贵）。分两阶段：

1. **阶段一 · 免费粗筛**（覆盖约 80%）
   用分区名、UP 主自带 tag、标题/简介关键词与同义词表（"美食"↔ 探店/试吃/食谱/厨房/料理）打分，同时用 embedding 算标题与主题词的语义相似度（本地 `bge-m3`，无 API 成本）。
   高分直接入选，低分直接淘汰。
2. **阶段二 · 边缘案例才用 LLM**（约 20%）
   仅对处于阈值带的候选，批量（一次 20 条标题+简介）交 LLM 判定，输出 `是/否 + 置信度`。成本压到原来的 1/10 以内。

判定结果**连同置信度一起展示**，并且用户可维护自己的主题词典（`topics.yaml`），越用越准：

```yaml
topics:
  摄影: { include: [镜头, 构图, 布光, 相机, 调色, 后期], exclude: [手机评测] }
  美食: { include: [探店, 试吃, 食谱, 料理, 厨房] }
```

## 6. 命令形态

```bash
# 只解析，看工具怎么理解你的话（调试用）
distill plan "影视飓风摄影方向最近半年播放量前20"

# 发现候选，出表格但不消化（默认行为，安全）
distill find "影视飓风摄影方向最近半年播放量前20"

# 确认后消化
distill find "..." --run
distill find "..." --run --yes --limit 10     # 脚本化，跳过确认

# 歧义时的交互示意
$ distill find "老师的专栏收藏量前100"
? 「老师」匹配到多个来源，请选择：
    1) 知乎专栏《…》 · 12.4 万关注
    2) B 站 UP 主「…」 · 88 万粉丝
? 「收藏量前100」的含义：
    1) 该专栏文章按被收藏数排序的前 100 篇
    2) 我的收藏夹里的前 100 篇
> 1 1
✓ 计划：知乎专栏《…》→ 按 favorite_count 降序 → 取 100
  假设：未限定时间，取全部历史文章
  预估：100 篇纯文本，无需 ASR，约 4 分钟，¥1.2（deepseek）
  继续？[Y/n]

# 把一次成功的发现固化为订阅（M4 用）
distill find "..." --save-as-subscription weekly-photo
```

**关键 UX 决策**：`find` 默认只发现不消化。先给你看候选表（标题 / 时长 / 播放 / 收藏 / 是否有字幕 / 主题置信度），你可以 `--exclude 3,7` 剔掉几条再跑。避免"一句话烧掉两小时算力"。

## 7. 项目结构增量

```
src/distiller/discover/
├── parser.py          # 自然语言 → Query IR（约束 JSON 输出）
├── clarify.py         # 歧义检测与反问策略
├── resolver.py        # 实体消歧：名字 → 平台 ID
├── providers/
│   ├── base.py        # DiscoveryProvider 抽象
│   ├── bilibili.py    # 含 WBI 签名、投稿列表、stat 补齐
│   ├── zhihu.py  xhs.py  rss.py
├── topic.py           # 两阶段主题判定
├── ranker.py          # 排序 + 平台能力补偿
├── planner.py         # dry-run 成本与耗时预估
└── topics.yaml        # 用户主题词典
```

## 8. 里程碑调整

Discovery 拆成两步插入，**不拖慢 M1 出可用版本**：

| 阶段 | Discovery 相关内容 |
|------|-------------------|
| M1 | 不含。仍是 `add <URL>`，先把「消化 + 浓缩」跑通 |
| **M2.5（新增）** | Query IR 解析 + 反问 + **B 站 UP 主投稿发现** + 主题漏斗 + dry-run 确认 + `find` 命令 |
| M3 | 知乎专栏 / 收藏夹发现；Web UI 里做候选勾选界面 |
| M4 | `find` 固化为订阅，定时增量抓取 → 每日高密度简报；小红书降级支持 |

理由：Discovery 的价值依赖于「消化质量已经可信」。先做发现会导致一次抓 50 个视频但摘要质量不达标，白烧算力。

## 9. 主要风险

| 风险 | 应对 |
|------|------|
| 一句话炸出几百条，算力/费用失控 | dry-run 强制确认 + `limits.monthly_budget_usd` 硬护栏 + 默认 Top20 |
| B 站 WBI 签名规则变动导致失效 | 签名逻辑单文件隔离，附自检命令 `distill doctor`；失效时降级到"手动贴 URL 列表" |
| 请求过频被限流/封禁 | 令牌桶限流 + 随机延迟 + 元数据缓存 + 断点续跑 |
| 主题判定误召回（把无关内容也消化了） | 展示置信度 + `--strict` 模式 + 候选表人工剔除 + 用户词典迭代 |
| LLM 把人话解析错 | `distill plan` 可先看解析结果；`assumptions` 全部显式展示，错了当场改 |
| 「收藏量」等指标无法精确获取 | 明确标注为近似值并说明候选池口径，不伪装精确 |
